## 一、前言

### （一）为什么要用pi

harness有相当多功能，是在上下文里雕花，会影响大模型注意力。pi的默认上下文相当简洁：

这是我已经配置过扩展的上下文占用，如果你用claude，可以/context对比看下。

![](https://pic2.zhimg.com/v2-2889dc1a23358e1f6f8d5ac4822b0887_1440w.jpg)

大模型参数变多、能力变强、花费变多，那些靠冗长上下文约束模型行为的，重harness，“正在”或者说“将要”退出历史舞台，**轻harness是一种趋势**
。

有篇博客做过评测，不同harness配不同顶级模型，任务通过率和花费的比较。

感兴趣的可以看原文：[博客链接](https://link.zhihu.com/?target=https%3A//www.databricks.com/blog/benchmarking-
coding-agents-databricks-multi-million-line-
codebase)。评测要花财力与精力，我不愿验证，姑且相信。这里贴对比图。

![](https://pica.zhimg.com/v2-e44c2f2dbd9699c59d5e392c65db101c_1440w.jpg)

可以看到，pi agent用同样的模型，通过率与花费的比值，领先codex与claude code。

pi
agent作者的设计理念相当克制，感兴趣的可以看看他的博客：[博客链接](https://link.zhihu.com/?target=https%3A//mariozechner.at/posts/2025-11-30-pi-
coding-agent/)

我简单概括下：

  * 最小化系统提示词与工具定义，顶尖模型经过了大量的强化学习训练，精简上下文也能做的很好。
  * 默认yolo模式，所有命令全放行，模型总能找到办法绕过命令权限，玩别怂怂别玩。
  * 没有todo，可以用todo.md去控制。
  * 没有plan模式，可以用plan.md去控制。如果想要只读，可以通过启动参数限制工具使用：

    
    
    pi --tools read,grep,find,ls

  * 没有MCP支持，MCP工具定义太多，占用上下文，鼓励用cli与外部交互。
  * 没有后台运行命令，后台进程管理增加了复杂度，而且可控性差（因为不怎么看），鼓励终端多开。
  * 没有子代理，子代理可控性差（因为不怎么看），黑盒中的黑盒，鼓励让pi生成自己。
  * 并不是完全否定子代理，但并行使用多个子代理实现功能，可能造出屎山，增加技术债务。

### （二）为什么不要用pi

如果你用的不是顶级模型，那你可能还需要多余的提示词，约束大模型行为。

比如：你是一个务实的工程师，你在动手编码前，先思考。

顶级模型已经不需要了。

再就是，pi
agent实在太毛坯房了，不带联网搜索、不支持为每个模型单独配置思考强度、不支持MCP、不支持子代理、没有命令权限控制、没有todo、没有goal、没有plan。

如果你用惯了opencode、claude code、codex，想要无痛切换到pi。是不可能的。

想找回那些熟悉功能的话，要去社区找扩展实现，或者自己实现。

保留的习惯越多，在DIY上花的时间精力就越多。

社区的扩展良莠不齐，很多也是vibe coding的。扩展出问题的时候，维护成本，就转移到了社区开发者上。

你可能觉得claude code实现得不好，还要捆绑着让你用。但社区开发者，同样有过度设计、维护不勤、水平参差不齐、重复造轮子的问题。

好在pi的架构设计，方便DIY，提高了社区扩展的平均水平。

总的来说：

  * 用惯了opencode、claude code、codex，想要无痛切换的，慎用。
  * 想要开箱即用，all in one，不想付出时间精力的，慎用。
  * 用的不是顶级模型的，需要很多提示词约束大模型行为的，慎用。

这篇毛坯房装修踩坑，就是为上述的人准备的。

## 二、bash环境

windows用户要注意：pi在win上需要git bash或wsl环境，不要使用powershell或cmd。

为什么不要使用powershell？搜一下“gpt大战powershell”。

pi按照以下顺序查找bash：

  1. `~/.pi/agent/settings.json` 中 `shellPath` 指定的路径
  2. `C:\Program Files\Git\bin\bash.exe`（Git Bash）
  3. PATH 中的 `bash.exe`（可能是 Cygwin、MSYS2、WSL 等）

如果你安装了git，但pi找不到bash，或者找到了错误的bash：

  1. 检查bash路径，cmd中where bash，确认第一位bash路径。
  2. 如果git bash不在第一位，去编辑环境变量，把`你的git路径\Git\bin` 添加到环境变量，移到最前面。或者在 `~/.pi/agent/settings.json` 中设置 `"shellPath": "你的git路径\\Git\\bin\\bash.exe"` 指定

### （二）pi-rtk-optimizer

命令输出优化。

比如你让agent查一下仓库历史

很可能给你跑git log这个命令，会很长。

### （三）pi-fff

rust写的，提高grep、find效率。

我会设置环境变量PI_FFF_MODE=override，覆盖自带的工具。

### （四）rpiv-web-tools

可以接exa联网搜索，我比较爱用exa。

可以fetch网页内容，需要js渲染的也支持。

识别到github链接时，可以clone到本地缓存，方便查看里面的代码。

  

不用pi-web-access的原因：

  * 它联网搜索，是这样的逻辑，调用web-search工具，搜索接口（比如exa）返回很多搜索结果，用配置的模型进行总结，有 手动批准/自动批准/不总结 三种模式，默认是手动批准很麻烦，模型总结容易丢信息，不总结占用的上下文又很长。exa返回的搜索结果，本来质量就比较好，不用搜那么多，也就不需要额外总结了，直接放进上下文，rpiv-web-tools就是后者。
  * 它网页内容获取，需要js渲染的，它就获取不到了，而rpiv-web-tools可以。
  * 添加的工具定义很多，web_search、fetch_content、get_search_content、source_check，增加了不必要的复杂度。

尽管它下载量是最高的，也不要用。

### （五）pi-chrome

浏览器控制，在你的浏览器安装扩展，来控制浏览器。能使用真实的登陆态。

比如打开已登陆的bilibili，获取底下的评论。

  

不用pi-agent-browser-native的原因：

  * 它用的是agent-browser这个项目，这个项目对win兼容很差，导致我用不了真实登陆态。

不用playwright、Puppeteer、Selenium的原因：

pi-
chrome作者写的方案对比：[对比](https://link.zhihu.com/?target=https%3A//cdn.jsdelivr.net/npm/pi-
chrome%400.15.46/docs/COMPARISON.md)

  

pi-chrome还有一个好处，没有添加工具定义。

你授权后，agent才会控制你的浏览器，授权前，agent不知道有这个工具。

浏览器控制配合前面的rpiv-web-tools使用，只有fetch不到的网页，才需要浏览器控制。

低频任务不进上下文。

### （六）pi-observational-memory

记忆功能，对话长了，可以记住前面的信息。比pi自带的压缩好。

  

其他记忆功能，没用过，不知道。

我比较喜欢让模型总结对话记录成md，保存到本地当做记忆，与后面的会话进行交接。

我这种方法是串行的、要人工审核的、可控性高的、但是累的。

pi-observational-memory是并行的、后台的、可控性低的、但是省心的。

### （七）pi-context-usage

提供了/context命令，显示上下文占用

### （八）pi-jingle

完成时发送提示音

agent跑完一轮，也就是没有调用工具，而输出回答的时候，发送提示音。

我一般在agent跑的时候，刷会手机，怕刷忘了，需要提醒我一下。

用的是时之笛的navi，柔和亲切。

### （九）narumitw/pi-btw

btw功能，临时问一个问题。用过claude code的都不陌生。

  

相比其他的btw扩展，它支持markdown渲染。

### （十）rpiv-ask-user-question

弹出一个窗口，问你一些问题，多选或是单选。

在你不知道它 懂你意思 还是 不懂你意思 的时候，这个功能很方便。

比如说，跟agent说，帮我把这个流程，做成用户级skill。

它可能 不懂你意思，用户级是什么，是为用户创建的，然后放在项目目录。

其实用户级，指的是放在~/.pi/agent/skills/

这个功能，避免它闷头苦干然后做错。

### （十一）pi-workspace-history

可以让pi的/tree功能，实现工作区级回滚，类似于opencode的 undo/redo。

比如说对话中，pi修改代码，你不满意，想回滚回修改前，这个扩展会很方便。

经过验证后重新采用，这个插件有两个设计问题，使用前需要注意：

  1. 不要设置影子 git 仓库路径在工作目录。默认在 ~/.pi/agent/state/workspace-history，如果你把 workspaceHistory.storageDir 改到工作目录内，每次提交都会提交仓库自身，导致存储膨胀。
  2. /tree 回滚默认连文件修改一起回滚，没法只回滚对话。

### （十二）没有选择的扩展

MCP相关，不用MCP，用CLI。

TODO相关，不用TODO。

子代理相关，不用子代理，并行操作的场景多开。如果需要的子代理太多，就要考虑技术债务了。

命令权限控制相关，个人不需要。倒是可以装，防止删库。

pi-tool-display，它修改了pi自带的工具定义，工具会多一些输出，用于它的display。如果你有其他扩展修改了pi自带的工具定义（pi-
fff），要配置那些工具，不对它们定义进行修改。衡量下来，不值得为了美观引入复杂度。
