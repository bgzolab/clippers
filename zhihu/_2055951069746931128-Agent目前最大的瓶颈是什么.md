我个人觉得，最大的瓶颈还是上下文。

排除掉玩具项目，我个人近三十年来，做过的项目中，最小的项目库，尺寸是6.2M，正常的中等项目库在5~10M这个级别并不少见。在现实的软件开发中，大点的50~100M，超大型项目库500M~1G甚至几个G的项目也并不少见。就算你埋怨这些玩意是屎山，但屎山的重点在于「山」而不是屎，意思是他们的规模都会极为庞大，1M以内的玩意甚至都很少被称为一个项目，更不用说被叫成屎山。

1M 以内的项目确实只在玩具项目中见到。哪怕 lua 解释器这么迷你的东西，它也是大于 1M 的。1M上下文不够放进任何非玩具意义的项目，然而很多新手还在为
vibe coding 出几百K的玩具项目而沾沾自喜。

而目前，就算大模型，也只是堪堪1M上下文而已，其中能够有效用上的也只有 200k，装更多内容时多少会有注意力问题。

那么问题来了，把我最小的项目 6M，也只能充其量装个 600K
进当前的大模型（留一些其它的给系统提示词跟harness用），十分之一的项目理解，某种意义上就是**盲人摸象** 。

  

为了解决**盲人摸象**
的问题，大模型每次都得从零记忆开始，然后不断的到各种位置去临时采集数据，以确保尽可能精准的只采集自己需要的数据，而避免灌进所有内容。

通常认为人类的记忆大约在几十G这个级别，这意味着它的内容是大模型1M上下文的数万倍。所以，领导吩咐人类做事的时候，并不需要先帮人类整理好上下文，不需要帮人类精简上下文，因为人类的上下文是几十G。而AI就不同了，它就是几百K不到1M的上下文，再聪明的脑袋瓜，只给这点上下文，能做的事跟判断也有限啊。

因此，就个人经验来看，大模型上下文的限制，是当今AI coding
一切技术的基础，所有技术都围绕着这个话题：在上下文极度受限的情况下如何把事情描述清楚并完成。

在G级别数据的时代，大家要面临一台只能处理M级别甚至K级别的数据的AI，并且让它把活儿干好，确实是头发都愁白了。

补充1：有人说人类的记忆其实对应了权重而不对应上下文，但评论区知友已经给大家解释了，人类可以随着项目跟行业成长调整自身权重，而大模型只能训练公共知识获取权重，那么属于行业私域以及项目相关的内容，可不就只能塞进上下文了么？如果大模型可以动态调整权重，那确实无需长上下文。但现实并不能。

补充2：我们确实有很多办法来给大模型做数据，比如生成项目概要，目录结构，总体设计文档等等各种东西，我们在驾驭工程，循环工程所做的很多事都在努力改进它造成的影响。但所有的机制都没有改变一个事实，ai读代码就是盲人摸象。它能够容纳的总知识很有限，无论你摸的这部分多么真实多么完备，但它都只是概要，而不是全貌。评论区很多秀优越感，你能理解所有的努力都没有改变ai事实上是在盲人摸象这个本质吗？

  

如果不明白我说的意思，假想一下，现在的电脑通常内存在 G 级别，8G，16G，32G，但如果给你一个 1M
内存（可用640K基础空间）的电脑，你能拿它干什么？

是的，当你觉得大模型傻，AI有幻觉的时候，要明白，其实现在的AI就是在**盲人摸象** 。
