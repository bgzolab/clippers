## 自 Petzold 之后，微软再无连贯的 GUI 战略

几年前，我参加了一个开发者会议，有人抛出了一个简单的问题：“现在开发一个新的 Windows 桌面应用，最推荐的框架是什么？”

全场死一般的寂静。

接着，一个人建议用 WPF；另一个人提到了 WinUI 3；第三个人则反问是不是干脆直接用 Electron
算了。会议从此彻底跑偏，那个问题最终也没能得到答案。  

那阵沉默就是故事的核心。而这个故事，要从三十多年前说起。  

**当一个平台无法在 10 秒钟内回答“我该如何构建 UI”时，它就已经辜负了它的开发者。不接受反驳。**

## Windows 最后一次给出清晰答案的时候

1988 年，查尔斯·佩佐尔德（Charles Petzold）出版了《Windows 程序设计》（ _Programming Windows_ ）。852
页，纯 C 语言编写的 Win16 API。尽管篇幅宏大，它却代表了一件了不起的事：关于如何编写 Windows
应用程序，它给出了一个单一、连贯且权威的答案。在业界，我们称之为“战略”。

随后的 Win32 虽然体量更大，但逻辑依然连贯：消息循环（Message loops）、窗口过程（Window
procedures）、GDI。这套心理模型虽然有点古怪，但它至少是**统一** 的。Petzold 讲透了它。它是 Windows 世界的
F=ma，简单、强大。你学习它，使用它，然后通向成功。

**清晰是开发者最好的朋友！** 一个操作系统，一套 API，一种语言，一本书。当时没有委员会在争论托管代码（Managed-code）的替代方案。只有
Win32 和
Petzold，而且这套组合拳确实有效。这是“物理学”，而不是“化学”——那种只有针对周期表里的某一小块才有效、且必须在特定压力、特定温度，还得赶上月亮运行到木星第七宫时才能起效的玄学。

接下来的故事，则是一场教科书级的演示：一家拥有天才员工和巨量资源的巨头，是如何通过优化错误的指标，制造出一场持续三十年的“世纪大乱炖”（Boof-a-
rama）的。通俗点说，就是**聪明人干了一堆蠢事** 。

## 面向对象的白日梦（1992–2000）

Win32 确实有局限性，所以微软拿出了他们的传统艺能：在开发者大会上发布新玩意儿。而且一发就是好几个。

1992 年诞生的 **MFC** 用 C++ 包装了 Win32。如果说 Win32 不够优雅，那么 MFC 就像是让 Win32
穿上了一件由其他西服缝成的燕尾服。紧接着是 OLE、COM、ActiveX。这些本质上都不是真正的 GUI 框架，而是组件架构，但它们渗透到了
Windows 开发的每一个角落，并引入了极高的认知复杂度——高到让克尔凯郭尔（哲学家）的著作读起来都像海明威的小说一样简练直白。

九十年代末，我听了一场讲座，试图弄明白 OLE 文档、COM 对象和 ActiveX
控件之间的区别。整整一个小时，我看着台上讲师的眼神，就好像他嘴里叼着半截耗子尾巴一样不可理喻。

微软当时推销的不是一个连贯的故事，而是一堆原始的技术构件，然后告诉开发者：“你们自己去拼凑故事吧。”这就是所谓的“发布会式乱象”——微软致力于优化的目标是让高管在
Keynote 演示中惊艳四座，而不是开发者或用户的最终成功。

## PDC 2003 与那个自我吞噬的愿景

在 2003 年的 PDC 大会上，微软揭晓了 **Longhorn**
。坦白说，那是微软向开发者展示过的最动人的技术愿景之一。它有三大支柱：WinFS（关系型文件系统）、Indigo（统一通信）以及 Avalon（即后来的
**WPF** ）。Avalon 是一个由 GPU 加速、基于矢量、并由名为 XAML 的声明式 XML 语言驱动的 UI 子系统。开发者看到 Avalon
的演示时都疯了——这才是正确的愿景。

然而，用吉姆·阿尔钦（Jim Allchin）在 2004 年 1 月内部备忘录中的话来说，这玩意儿就是个“烂摊子”（A pig）。

到了 2004 年 8 月，微软宣布开发工作彻底重启。全废掉，从 Server 2003
的代码库重新开始。重启之后，高管下达了一条缄默指令：**Windows 内部不准再碰那该死的托管代码。** 所有新代码必须用 C++ 编写。WPF 虽然随
Vista 一起发布，但系统外壳（Shell）本身绝不使用它。

Windows 团队对 .NET 的怨念从未愈合。在他们看来，押注新的托管代码框架导致了公司历史上最尴尬的失败。这种怨念在 Windows 团队和 .NET
团队之间引发了长达 13 年的机构内战，最终导致了 WPF 成为弃儿、Silverlight 被处死、UWP 走向毁灭，并留给了我们今天这个支离破碎的
GUI 生态。

## Silverlight：套路初成（2007–2010）

WPF 在 2006
年底发布，它非常出色：XAML、硬件加速渲染、真正的双向绑定。如果微软当时把它定为唯一的标准并持续投入，结局可能会大不相同。然而，2007 年，他们推出了
**Silverlight** ：一个旨在与 Flash 竞争的精简版浏览器插件，跨平台、优雅，且后来成为了 Windows Phone 的基石。到
2010 年左右，它看起来就像是富客户端的未来。

然而在 MIX 2010 大会上，一位微软高管在问答环节表示，Silverlight 不再是跨平台战略的重点，它现在的定位是 Windows
Phone。HTML5 成了新政策。Silverlight 团队甚至都没被提前告知。那些把自己核心业务（LOB）应用押注在 Silverlight
上的开发者，居然是通过一场发布会的 Q&A 才得知死讯的。

Silverlight 并不是死于技术失败，它的技术很棒。它死于商业战略的横跳，而开发者总是最后一个知道被卖掉的人。

记住这个套路，后面还会出现。

## Metro 式恐慌与双团队战争（2012）

当时，苹果已经卖出了 2 亿台 iPhone，iPad 正在蚕食 PC 市场。微软的答案是 Windows 8 和 **Metro** ——一套名为
WinRT 的触控优先运行时，而且是刻意**不** 基于 .NET 构建的。还记得 Windows 团队的怨念吗？就在这里爆发了。WinRT 是原生 C++
运行时，与 WPF、WinForms 以及开发者在 .NET 上十年的投入彻底割裂。

当时微软内部其实同时讲着两个故事：Windows 团队在搞 WinRT，.NET 团队还在宣扬 WPF。不同的办公楼，不同的副总裁，不同的路线图。

开发者在 Build 2012 大会上听到了什么？未来是 WinRT，但 HTML+JS 也是一等公民，同时 .NET 还能用，C++ 也回归了，你应该写
Metro 应用，不过你的 WPF 代码运行起来也还没问题。  
**这不叫战略。这是《饥饿游戏》的竞技场，六个团队正在为了争夺你的注意力而自相残杀。**

企业开发者看了一眼 UWP 的沙盒限制、应用商店强制部署要求以及缺失的 Win32
API，然后头也不回地走了。这套本意是赢回现代开发者的框架，却为了一个从未实现的平板应用商店梦而过度优化。

## UWP 与 WinUI 的野蛮生长（2015 至今）

Windows 10 带来了 **UWP** （通用 Windows
平台）——号称“一次编写，到处运行”（PC、手机、Xbox、HoloLens）。纸面上很诱人，现实却很骨感：Windows Phone
快死了，而且微软自家的旗舰应用（Office、Visual Studio 甚至系统外壳本身）都没在用 UWP。即便没人明说，信息也已经传达得很清楚了。

当 UWP 停滞不前时，官方给出的答案变成了“视情况而定”：新应用用 UWP，老应用留守 WPF，通过 XAML Islands 添加现代 API，等一等
WinUI 3。哦对了，WinUI 2 是专门给 UWP 用的，然后 Project Reunion 会解决一切……等下，我们把它改名成了
**Windows App SDK** ，而且它还是不能完全替代 UWP，并且……

聪明人干的蠢事。技术界的布朗运动。

Project Reunion / WinUI 3 确实代表了真正的进步。但请问：这个坑最初是怎么挖出来的？UWP 的控件之所以和系统深度绑定，是因为
Windows 团队拥有它们。而 .NET 团队不拥有，工具团队也不拥有。Project Reunion 本质上是一个披着技术方案外衣的“组织架构补丁”。

一位开发者在 2024 年总结道：“我一直紧跟着微软的变迁：UAP、UWP、被 C++/WinRT 取代却没工具支持的 C++/CX、XAML
Islands、XAML Direct、Project Reunion、重启的 WinAppSDK、WinUI 2.0 和 3.0 之间的混乱切换……”整整
14 年，14 次反复。这位开发者值得一枚勋章，以及一句道歉，按顺序一个个来。

## 没人看管的动物园

以下是微软目前仍在出货的所有 GUI 技术：

**微软原生框架：**

  * **Win32 (1985)** ：还在，还在用，Petzold 的书依然有效。
  * **MFC (1992)** ：Win32 的 C++ 包装，维护模式，活跃在企业级和 CAD 领域。
  * **WinForms (2002)** ：Win32 的 .NET 包装，“可用但不鼓励”。写填表程序依然最快。
  * **WPF (2006)** ：XAML 驱动，DirectX 渲染，已开源。微软已无新投入。
  * **WinUI 3 / Windows App SDK (2021)** ：“现代”答案。路线图不明。
  * **MAUI (2022)** ：Xamarin.Forms 的跨平台接班人。.NET 团队目前的筹码。

**微软 Web 混合方案：**

  * **Blazor Hybrid** ：在原生 WebView 里跑 .NET Razor 组件。
  * **WebView2** ：在 Win32/WinForms/WPF 里嵌入 Chromium。

**第三方势力：**

  * **Electron** ：Chromium + Node.js。VS Code、Slack、Discord 都在用。它是目前 Windows 上部署最广的桌面 GUI 技术——而微软对此毫无贡献。
  * **Flutter (Google)** ：Dart 语言，自定义渲染，跨平台。
  * **Tauri** ：Rust 后端，轻量级 Electron 替代品。
  * **Qt** ：C++/Python/JS。严肃的跨平台选型。
  * **React Native for Windows** ：微软背书的 Facebook 移动框架移植版。
  * **Avalonia** ：开源的 WPF 精神续作。JetBrains、GitHub、Unity 等不再等待微软的开发者都在用它。
  * **Uno Platform** ：让 WinUI API 跑在所有平台上。他们对 WinUI 的投入程度甚至超过了微软自己。
  * **Delphi / RAD Studio** ：还活着，还很快，依然活跃在垂直市场。
  * **Java Swing / JavaFX** ：是的，仍在生产环境中使用。企业级市场从不遗忘。

17 种方案，5 种编程语言，3 种渲染哲学。这不叫平台**。** 虽然我无法给“大乱炖”（Boof-a-
rama）下一个字典定义的准确说明，但当我看到这副景象时，我知道就是它了。

## 启示录

每一次失败的 GUI 尝试都能归结为三个原因：内部团队政治（Windows vs. .NET）、为了在开发者大会上博眼球而推出的早产方案（Metro,
UWP），或者是毫无预警地抛弃开发者的商业战略转向（Silverlight）。这些没有一个是技术上的失败。这些技术往往真的很棒——WPF
很棒，Silverlight 很棒，XAML 也很棒。真正失败的产品，是微软的**组织架构** 。

你要么拥有一套涵盖全生命周期（采用、投入、维护、迁移）的“逻辑自洽的成功理论”，要么你就只拥有一个开发者大会的 Keynote。

前者叫战略，后者叫一场持续三十年的“大乱炖”。

查尔斯·佩佐尔德为了跟上微软发布的每一个新玩意儿，曾先后写了六版《Windows 程序设计》。在写完针对 Windows 8 / WinRT
的第六版后，他停笔了。那是 2012 年。

我不怪他。

## 关于作者 Jeffrey Snover

Jeffrey Snover 现已功成身退，目前正以“**游侠哲学家** ”（Philosopher-
Errant）的身份行走江湖，流连于各大科技会议并发表公开演讲。在 2026 年光荣退休之前，他曾是 Google 的杰出工程师（Distinguished
Engineer）以及微软的技术院士（Technical Fellow）——在微软任职期间，他曾担纲 Office 部门的 AI 架构师，并出任
Windows Server Azure Stack 的首席架构师。

当然，Snover 最为江湖称道的名号是 **Windows PowerShell 之父** 。正是他发明了这一基于对象的分布式自动化引擎、脚本语言兼命令行
Shell。

Snover 于 1999 年加入微软，担任管理与服务事业部的部门架构师，为微软旗下的管理技术与产品指点江山，提供技术统筹。

在加入微软之前，他已手握 8 项专利，此后又陆续斩获了 30 多项。作为业界和研究性会议上的常客，他聊起管理和语言类话题来总是滔滔不绝。
