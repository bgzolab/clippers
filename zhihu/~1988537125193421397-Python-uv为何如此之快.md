uv 安装软件包的速度比 pip 快一个数量级。通常的解释是“它是用 Rust 写的”。这没错，但这并不能解释太多。很多工具都是用 Rust
写的，但速度并不快。真正有趣的问题是，究竟是哪些设计决策造就了这种差异。

Charlie Marsh 在[Jane Street
的演讲](https://link.zhihu.com/?target=https%3A//www.janestreet.com/tech-
talks/uv-an-extremely-fast-python-package-manager/)以及[Xebia
工程团队的深度解析](https://link.zhihu.com/?target=https%3A//xebia.com/blog/uv-the-
engineering-secrets-behind-pythons-speed-
king/)已经很好地涵盖了技术细节。真正有趣的是设计决策：例如，实现快速路径的标准、uv drop舍弃的功能（pip仍支持），以及完全不需要 Rust
的优化。

## 使uv成为可能的标准

pip 速度慢并非实现上的缺陷。多年来，Python 打包都需要执行代码才能确定软件包需要哪些组件。

问题出在[setup.py
文件](https://link.zhihu.com/?target=https%3A//setuptools.pypa.io/)上。如果不运行软件包的
setup 脚本，就无法了解其依赖项。但又不能在不安装其构建依赖项的情况下运行 setup 脚本。2016年的[PEP
518](https://link.zhihu.com/?target=https%3A//peps.python.org/pep-0518/)明确指出了这一点：“如果不了解
setup.py 文件的依赖项，就无法执行它；但目前还没有标准方法可以在不执行 setup.py 文件的情况下自动获取这些依赖项。”

这种先有鸡还是先有蛋的问题迫使 pip 下载软件包、执行不受信任的代码、失败、安装缺失的构建工具，然后重试。每次安装都可能导致一系列子进程的生成和任意代码的执行。安装源代码发行版本质上也需要`curl | bash`额外的步骤。

修复工作分阶段进行：

  * [PEP 518](https://link.zhihu.com/?target=https%3A//peps.python.org/pep-0518/) (2016) 创建了 pyproject.toml 文件，为软件包提供了一个无需执行代码即可声明构建依赖项的地方。TOML 格式借鉴自 Rust 的 Cargo，这使得 Rust 工具回归修复 Python 打包问题显得不那么巧合了。
  * [PEP 517](https://link.zhihu.com/?target=https%3A//peps.python.org/pep-0517/) (2017) 将构建前端与后端分离，因此 pip 不需要了解 setuptools 的内部结构。
  * [PEP 621](https://link.zhihu.com/?target=https%3A//peps.python.org/pep-0621/) (2020) 规范了该`[project]`表，因此可以通过解析 TOML 而不是运行 Python 来读取依赖关系。
  * [PEP 658](https://link.zhihu.com/?target=https%3A//peps.python.org/pep-0658/) (2022) 将包元数据直接放入 Simple Repository API 中，以便解析器无需下载 wheel 即可获取依赖关系信息。

PEP 658 于 2023 年 5 月在 PyPI 上正式发布。uv 于 2024 年 2 月推出。uv
之所以速度快，是因为其生态系统终于具备了支持它的基础设施。像 uv 这样的工具在 2020 年是不可能发布的，因为当时的标准尚未完善。

其他生态系统更早地解决了这个问题。Cargo 从一开始就使用静态元数据。npm 的 package.json 文件是声明式的。Python
的打包标准最终使其与 Cargo 保持一致。

## uv舍弃了哪些功能

速度源于排除法。每少一条代码路径，就意味着少一条等待的代码路径。

UV的[兼容性文档](https://link.zhihu.com/?target=https%3A//docs.astral.sh/uv/pip/compatibility/)列出了它不具备的功能：

**不支持 .egg 文件。.egg** 文件是 wheel 出现之前的二进制文件格式。pip 仍然支持这种格式；uv
甚至都不尝试支持。这种格式已经过时十多年了。

**不依赖 pip.conf 文件。uv** 完全忽略 pip 的配置文件。不进行解析，不查找环境变量，也不继承系统级和用户级的配置。

**默认情况下不进行字节码编译。pip** 在安装过程中会将 .py 文件编译为 .pyc 文件。uv
会跳过此步骤，从而缩短每次安装的时间。您可以选择启用此功能。

**需要虚拟环境。pip** 默认允许将 Python 安装到系统 Python 中。uv 则相反，除非明确指定参数，否则不会修改系统
Python。这省去了大量的权限检查和安全代码。

**更严格的规范执行。pip** 会接受那些技术上违反打包规范的格式错误的软件包，而 uv 则会拒绝它们。容忍度越低，回退逻辑就越少。

**忽略 requires-python 的上限。** 当一个包声明需要 Python 版本时`python<4.0`，uv
会忽略上限，只检查下限。这大大减少了解析器的回溯，因为上限几乎总是错误的。包声明需要 Python 版本`python<4.0`是因为它们尚未在
Python 4 上进行测试，而不是因为它们实际上会出错。此约束是防御性的，而非预测性的。

**默认情况下，使用首选索引。** 如果配置了多个包索引，pip 会检查所有索引。uv
会从第一个包含所需包的索引开始查找，并在此停止。这可以防止依赖关系混淆攻击，并避免额外的网络请求。

这些都是 pip 必须执行而 uv 不需要执行的代码路径。

## 不需要 Rust 的优化

uv 的部分速度提升得益于 Rust，但远没有你想象的那么多。pip 目前就可以实现几个关键的优化：

**使用 HTTP 范围请求来获取元数据。** [Wheel
文件](https://link.zhihu.com/?target=https%3A//packaging.python.org/en/latest/specifications/binary-
distribution-format/)是 zip 压缩包，而 zip 压缩包会将文件列表放在末尾。uv 首先尝试使用 PEP 658
元数据，如果不行则回退到使用 HTTP 范围请求来获取 zip 压缩包的中心目录，然后下载完整的 wheel
文件，最后从源代码构建。每一步都会变得更慢、风险更大。这种设计使得快速路径能够覆盖 99% 的情况。所有这些都不需要 Rust 语言。

**并行下载。pip** 一次下载一个软件包，而 uv 一次下载多个。任何语言都可以做到这一点。

**使用硬链接的全局缓存。pip** 会将软件包复制到每个虚拟环境中。uv
则只保留一份全局副本，并使用[硬链接](https://link.zhihu.com/?target=https%3A//en.wikipedia.org/wiki/Hard_link)（或在支持的文件系统上使用写时复制）。将同一个软件包安装到十个虚拟环境中占用的磁盘空间与安装到一个虚拟环境中占用的磁盘空间相同。任何具有文件系统访问权限的语言都可以做到这一点。

**无需 Python 即可完成解析。pip** 需要 Python 运行才能执行任何操作，并且会调用构建后端作为子进程来获取旧版软件包的元数据。uv
可以原生解析 TOML 和 wheel 元数据，只有在遇到仅包含 setup.py 文件且别无选择的软件包时才会启动 Python。

**PubGrub 解析器。uv** 使用了[PubGrub
算法](https://link.zhihu.com/?target=https%3A//github.com/dart-
lang/pub/blob/master/doc/solver.md)，该算法最初来自 Dart 的 pub 包管理器。pip 和 PubGrub
都使用了回溯算法，但 PubGrub 应用了来自 SAT 求解器的冲突驱动的规则学习（conflict-driven clause
learning）：当遇到死胡同时，它会分析原因并跳过后续类似的死胡同。这使得它在处理复杂的依赖关系图时速度更快，并且能够更好地解释失败原因。pip
可以采用 PubGrub 而无需用 Rust 重写。

## Rust 真正发挥作用的地方

某些优化确实需要用到 Rust：

**零拷贝反序列化。uv**
使用[rkyv反序列化缓存数据](https://link.zhihu.com/?target=https%3A//rkyv.org/)[，](https://link.zhihu.com/?target=https%3A//nesbitt.io/2025/12/26/how-
uv-got-so-fast.html%23fn%3A1)无需复制数据。数据格式与内存格式相同。其他语言中也有类似 FlatBuffers
的库实现此功能，但 rkyv 与 Rust 的类型系统紧密集成。

**线程级并行。Python的 GIL
机制强制并行工作在单独的进程**[中](https://link.zhihu.com/?target=https%3A//nesbitt.io/2025/12/26/how-
uv-got-so-fast.html%23fn%3A1)进行，这会带来进程间通信 (IPC) 的开销和数据复制。Rust
可以原生支持跨线程并行，共享内存而无需序列化边界。这对于问题解析尤为重要，因为求解器需要探索多种版本组合。

**无需启动解释器。** 每次 pip 生成子进程时，都会产生一次 Python 启动开销。uv 是一个静态二进制文件，无需初始化运行时环境。

**紧凑的版本表示。uv** 尽可能将版本打包成 u64 整数，从而加快比较和哈希速度。超过 90% 的版本都能装入一个 u64
整数中。这种微优化在数百万次的比较中都能产生显著效果。

这些都是实实在在的优势。但与放弃旧版支持、采用现代标准所带来的架构优势相比，它们就显得微不足道了。

## 设计胜于语言

uv之所以速度快，是因为它省略了某些操作，而不是因为它使用了什么语言。PEP
518、517、621和658等标准使得快速的包管理成为可能。摒弃了eggs、pip.conf和宽松的解析方式，使得这一切成为可能。Rust则进一步提升了它的速度。

pip 明天就能实现并行下载、全局缓存和仅元数据解析。但它没有，主要是因为要优先考虑与过去十五年来的各种极端情况保持兼容。这意味着 pip
的速度永远比不上那些从零开始、基于现代假设的工具。

其他包管理器可以借鉴这种做法：静态元数据、无需执行代码即可发现依赖项，以及在下载前预先解决所有依赖问题。Cargo 和 npm
多年来一直采用这种方式。如果你的生态系统需要运行任意代码才能确定一个包需要什么，那么你已经失败了。
