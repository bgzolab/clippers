这几天知乎开放平台放出了一个新东西：zhihu CLI，官方配套的 Skill
也一并上线。简单说，就是知乎把站内搜索、全网搜索、热榜、直答，以及“我自己账号”的创作、关注、收藏数据，都封装成了命令行接口，AI 助手拿到一个
Access Secret 就能直接调用。

作为在知乎写了九年文章、攒下一千六百多条内容的作者，我第一反应是：这对创作者意味着什么新玩法？于是第一时间把它装上跑了起来。我总结了一下可能的玩法：

[知乎开放平台近期新推出的Zhihu CLI
能力，有哪些值得探索的玩法？](https://www.zhihu.com/question/2068735236100154306/answer/2069101060678013833)

安装过程中我发现一件很多人可能没注意到的事——知乎官方其实同时提供两种接入方式：除了这个新出的 Skill + CLI 组合，还有一套托管好的 MCP
服务，填个地址和密钥就能连。两种方式背后是同一套开放平台接口，用同一个 Access Secret，但形态和适用场景差别很大。

网上谈 MCP 的文章不少，但多数停留在概念层面，很少有人把两种方式都真装一遍再对比。这篇就按我在 Windows 11
上的实际操作来写：调用链路长什么样、功能差在哪、安全性谁强谁弱，都落到具体的命令和配置上。接口参数出自 Skill 包内附的官方文档（Skill
0.2.1，CLI 0.2.0，MCP 文档核验于 2026 年 7 月），安装细节是我的实测记录。想清楚了这两件事，后面谈“玩法”才有根基。

## Skill + CLI：一本说明书加一把扳手

这个方案分两层。Skill 是个 42KB 的纯文本压缩包，装进 AI
宿主的技能目录，里面没有任何二进制，只有使用说明（SKILL.md）、安装脚本和几份参考文档。它告诉
AI：什么场景调哪个命令、初始化怎么走、哪些事不许做。真正干活的是 zhihu-cli.exe，负责调接口、管凭证、处理重试和错误，最后吐 JSON
回来。我的理解是：Skill 是说明书，CLI 才是扳手。

跑通之后的调用链路是：我用自然语言提需求，AI 按 Skill 的指令通过终端权限系统调用 CLI，CLI 带着 Access Secret
向知乎开放平台发 HTTPS 请求，拿回 JSON 交给 AI 整理。如下图所示。

![](https://pic1.zhimg.com/v2-d9c0776e05800cb802e42a261443cdda_1440w.jpg)图 1

### 安装实录：Windows 上有个小坑

对于比较好的大模型，安装其实很简单：

    
    
    请下载安装 zhihu-cli skill 并完成初始化配置  https://developer-cdn.zhihu.com/zhihu-cli/releases/stable/skill/zhihu-cli-skill.zip

自己安装其实还是挺麻烦的，安装过程中踩了个值得一说的坑。Skill 自带的 run.ps1 是 UTF-8 无 BOM 编码，里面又有中文注释，在中文版
Windows 自带的 PowerShell 5.1 下会被误当 GBK 读取，直接报解析错误。手动给两个 .ps1 文件补上 UTF-8 BOM
之后才跑通。用 Windows 的朋友遇到同样问题，照此处理即可——这种事官方文档不会写，只有真装过才知道。

Skill 包本身不带 CLI 二进制。安装脚本会去知乎官方 CDN
拉发布清单，选当前平台的版本下载，然后连着做四道校验：官方域名、文件大小、SHA-256、二进制自报版本，全对得上才落盘到用户目录（Windows 下是
%LOCALAPPDATA%\ZhihuCLI）。不要管理员权限，也不动 PATH。这套供应链校验的严格程度，说实话比不少 Linux
发行版的包管理都讲究。

    
    
    # 状态检查（每个会话首次使用时跑一次）
    powershell -ExecutionPolicy Bypass -File <skill-dir>/scripts/run.ps1 status
    # 安装 CLI
    powershell -ExecutionPolicy Bypass -File <skill-dir>/scripts/setup.ps1
    # 配置 Access Secret：走标准输入，不进进程参数、不落 shell 历史
    printf '%s' '<access-secret>' | zhihu-cli auth set --secret-stdin
    # 在线验证凭证
    zhihu-cli auth status --verify

Secret 最终存进 Windows 凭证库。装完后我特意翻了安装目录和配置文件确认过：没有明文密钥，状态查询只回显掩码。

### 命令一览

CLI 把全部能力封成子命令，AI 通过绝对路径调用，不依赖 PATH。capabilities 子命令能返回机器可读的能力清单，每级 --help
都带参数约束和示例：

能力| 命令| 说明  
---|---|---  
知乎搜索| search zhihu --query "..." \--count 10| 知乎回答、文章等原始内容和链接  
全网搜索| search global --query "..." \--count 10| 站外新闻、官网等来源，支持 filter 筛选  
知乎热榜| hot --limit 20| 当前热点，最多 30 条  
知乎直答| answer --query "..." \--model zhida-fast-1p5| 检索增强的 AI 答案，支持流式输出  
我的创作| me contents --type all --limit 20| 本人账号的回答、文章、视频、想法、问题  
我的关注| me followees --limit 20| 本人关注的用户  
我的收藏| me favorites lists / items / recent| 收藏夹列表、夹内条目、近期收藏  
  
输出约定很干净：stdout 只给服务端原始 JSON，不裁字段、不改结构；stderr 只给诊断信息；出错返回稳定的 JSON
错误码加非零退出码。这套约定明显是照着“给程序消费”设计的，Agent 解析起来不用猜。一次真实的搜索调用长这样：

    
    
    $ zhihu-cli search zhihu --query "Agent Memory" --count 10
    {"Code":0,"Message":"success","Data":{"Items":[
      {"ContentType":"answer","Title":"...","AuthorName":"...",
       "Url":"https://www.zhihu.com/answer/...","Summary":"..."}],
     "Paging":{"IsEnd":false,"NextOffset":"10"}}}

## MCP：什么都不装，工具送上门

MCP 走的是另一个极端：本地什么都不用装。知乎官方托管了四项 MCP 服务，AI 客户端在配置文件里写上服务地址和 Access Secret，连上之后做
initialize 握手、tools/list 拉工具定义，然后模型就能在会话里随时调这些工具了。和 CLI
最大的区别是：工具列表常驻模型上下文，模型自己判断什么时候该调，不需要逐次显式触发。

![](https://pica.zhimg.com/v2-3b50f4a957c2232de4f259d176b54a1e_1440w.jpg)图 2
MCP 的调用链路：工具由服务端下发，常驻模型上下文

搜索类和热榜用 MCP over SSE：先连 SSE 端点换一个带 sessionId 的 message 地址，再往里发 JSON-RPC，结果从
SSE 通道异步回来。直答用更新的 Streamable HTTP，单端点搞定。四件事对应四个服务：

服务| 工具名| 传输方式| 端点  
---|---|---|---  
知乎搜索| zhihu_search| MCP over SSE| /api/mcp/zhihu_search/v1/sse  
全网搜索| global_search| MCP over SSE| /api/mcp/global_search/v1/sse  
知乎热榜| hot_list| MCP over SSE| /api/mcp/hot_list/v1/sse  
知乎直答| zhida| Streamable HTTP| /api/mcp/zhida/v1/stream  
  
鉴权统一是请求头带 Authorization: Bearer <your_access_secret>。返回的是 MCP text
类型，正文是面向模型消费的结构化 XML，官方建议整段原样喂给模型，不要自己裁字段。以热榜为例，裸协议调一遍长这样：

    
    
    # 1. 连 SSE，拿到带 sessionId 的 message 地址
    curl -N 'https://developer.zhihu.com/api/mcp/hot_list/v1/sse' \
      -H 'Authorization: Bearer <your_access_secret>' \
      -H 'Accept: text/event-stream'
    # 2. initialize 握手
    curl -X POST "$MESSAGE_URL" \
      -H 'Authorization: Bearer <your_access_secret>' \
      -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{...}}'
    # 3. 调工具，结果走 SSE 通道回来
    curl -X POST "$MESSAGE_URL" \
      -H 'Authorization: Bearer <your_access_secret>' \
      -d '{"jsonrpc":"2.0","id":3,"method":"tools/call",
           "params":{"name":"hot_list","arguments":{"limit":10}}}'

实际用的时候不用手写这些——MCP 客户端会把协议封掉，模型看到的只是四个现成的工具。上面这段 curl 是给想自己接协议的人看的。

## 功能对比：分水岭在“本人数据”

能力| Skill + CLI| MCP  
---|---|---  
知乎搜索| search zhihu（≤10 条）| zhihu_search（≤10 条）  
全网搜索| search global（≤20 条，filter / 索引库）| global_search（≤20 条，filter / 索引库）  
知乎热榜| hot（≤30 条）| hot_list（≤30 条）  
知乎直答| answer（三种模型，支持流式）| zhida（三种模型，默认整段返回）  
我的创作 / 关注 / 收藏| me contents / followees / favorites| 不提供  
安装升级与凭证管理| setup / upgrade / auth 系列| 无本地组件，不适用  
  
公共内容这块两者几乎完全对齐，连参数上限都一样——因为背后是同一套 API。拉开差距的是本人数据：CLI 独占 me 系列命令，能读当前 Access
Secret 所属账号的创作、关注、收藏；MCP 服务群目前完全没有这块能力。想在 AI
里用自己的创作数据做文章，比如统计历年产量、分析读者反馈、提炼写作风格，眼下只有 CLI 这条路。

另外两个小区别也值得知道。CLI 的 answer 支持流式 SSE 和终端打字机输出，MCP 的 zhida 默认等完整答案一次性返回，想要增量事件得绕过
MCP 直接用原生 HTTP 接口。输出形态上，CLI 给原始 JSON，适合程序解析和二次加工；MCP 给的是喂模型用的 XML，对 Agent
友好，对传统程序集成不那么友好。

至于两者的联系：同一个 Access Secret 通用，同一批后端接口，同一套配额和频率限制，数据边界一模一样。可以这么理解——CLI 是“AI +
本地环境”场景的封装，MCP 是“AI 客户端 / 多 Agent 工作流”场景的封装。官方 Skill 文档自己的说法也印证这点：日常任务优先用
CLI，只有开发接入才去读 HTTP API、OAuth、MCP 那些原始文档。

## 安全性

因为工作关系，最近同时在看CLI和MCP，知乎的CLI给我一个很好的观察切片。安全无疑是观察的一个重要方面。在安全性上CLI无疑是有优势的。这一条没什么好客气的。CLI
方案里，Secret 通过标准输入喂进去（不进进程参数，不落 shell 历史），由 CLI
写进操作系统凭证库，配置文件和项目目录里都没有明文，查状态只给掩码；连“环境变量覆盖了钥匙串”这种边角冲突（ENV_SHADOWS_KEYCHAIN）都有专门处理。MCP
那边，Bearer 令牌就明文躺在客户端配置文件里，谁读到这个文件谁就能拿走它。我装完 CLI 后专门检查过安装目录，确实找不到明文
secret——光凭这一点，日常个人使用我就会选 CLI。

### 攻击面：常驻工具的代价

MCP 的工具定义是服务端下发的、常驻模型上下文，这带来两类 MCP 圈子公认的风险：一是工具投毒，工具描述里夹带给模型的指令；二是 rug
pull，服务端事后悄悄改工具行为，客户端很难察觉。加上模型随时可能自主触发调用，返回内容里如果藏了提示词注入，命中概率被进一步放大。CLI
方案里每次调用都要过 AI 的判断和终端权限系统，SKILL.md
在本地、装之前可以逐行审查——我装的时候就把两个安装脚本通读了一遍，确认它只从官方域名下载、校验哈希、不动系统配置，才放它跑的。

公平起见也要说：返回内容注入是两者共有的风险。知乎社区内容对模型来说是不可信第三方数据，无论以 JSON 还是 XML
的形式进上下文，模型侧都得保持警惕，换传输方式并不能解决。

### 供应链：信任锚点放哪

CLI 的代价是本地多了个二进制，所以才有那套四重校验顶着：官方域名、大小、SHA-256、版本自报，装到用户目录、不要管理员权限，升级还支持回滚。MCP
没有本地二进制，供应链上是干净的，但代价是把信任整体押在远端服务的长期可靠上——服务端的任何变化你都得照单全收。两种方式只是信任锚点放的位置不同。

### 泼一盆冷水：平台侧的数据边界没变

不管走哪条路，你的搜索词、直答提问、本人数据请求，最终都进了知乎的服务器。传输方式改变的是本机这一侧的安全水位，不是平台侧的数据边界。指望换个接入方式就“数据不出圈”，是想多了。下面这张图把两种方案各维度的优劣放在一起对照。

![](https://pic3.zhimg.com/v2-ae254692de6b0b904f204b3f0d8803ea_1440w.jpg)图 3
安全维度对照（绿为优势项，红为风险项）安全维度| Skill + CLI| MCP  
---|---|---  
凭证存储| 系统凭证库，无明文落盘| 配置文件明文 Bearer  
调用触发| 显式调用，经权限系统| 工具常驻，模型可自主触发  
工具/指令定义| 本地 SKILL.md，可预先审查| 服务端下发，有投毒 / rug pull 风险

服务端数据暴露| 相同（同一后端）| 相同（同一后端）  
内容注入风险| 共有，触发面较小| 共有，常驻工具放大触发面  
  
## 我的选择

两种方式访问的是同一个知乎、同一份数据，差别在于把能力放在哪、把信任押在哪。MCP 胜在零安装、协议标准、客户端生态广，模型能自动编排调用，适合嵌进多
Agent 工作流或者快速接入了事的场景；代价是凭证明文落盘，工具常驻带来的攻击面也更大。Skill + CLI
胜在凭证进系统钥匙串、调用显式可控、指令和二进制都能审能校验，还独占了本人创作、关注、收藏数据能力。

所以，我肯定日常在本地 AI 环境里查资料、读自己的创作数据，只用 CLI。只有在写自动化工作流、需要标准协议对接多个客户端时才会考虑 MCP。
