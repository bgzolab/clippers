我认为好用的，至少绝对可用（不像某些玩具项目），不过是这个
[opencode](https://link.zhihu.com/?target=https%3A//github.com/anomalyco/opencode)
哈（下面简称 oc）。

我不是那种随便玩玩的用一下，到现在我怎么也用了至少小半年了。现在基本上日常开发工作全部使用 oc 完成，公司虽然提供了 500$ 额度的 cursor
套餐，但显然你如果是无脑用 opus 并不够你吸几次的，而且也是一笔不可忽略的项目预算，我目测公司早晚会因为预算过于昂贵而砍掉它。

其实要说 oc 和 cc 相差多少，这个很难评，一方面是因为 cc 本身不开源（虽然之前强开了一版），另一方面是 oc 和 cc 总归还是
agent，模型本身也是不可忽略的因素。所以很多文章或者人和你说 xxx 超级好用时，可能并没有把话说全，至少应该把使用哪个 model 加上。

而且，很多人总是在拿 cc 作为 oc 的未来形态去进行比较，认为 oc 最终会发展为下一个 cc，大错特错，你可以说它们都是 coding
harness，但从设计到实现，完全不沾边，具体可以看我在这个问题下的回答：

[Claude Code 源码泄露后OpenCode
却没有一波大更新？是开源社区躺平了，还是另有隐情？](https://www.zhihu.com/question/2053497628416030104/answer/2061141043538613239)

扯远了，回到问题本身吧。

oc 你要想和 cc 对比，首先本体是不够的，因为它的本地仅仅提供了 coding agent
那些最核心和基本的实现，关于应用层面的最佳实践，因为开源，注定是不能够带有太多的主观判定的，毕竟这个事情众口难调。

不过 oc 的解决方案就是 plugin，不是简单注册一些预设配置的那种 plugin 哈（其实更应该叫做 preset），而是可以直接扩展甚至改变 oc
本身行为的 plugin。

当前必装的 plugin 可能很多文章都会推 [oh-my-
opencode](https://link.zhihu.com/?target=https%3A//github.com/code-yeongyu/oh-
my-openagent)（后来改成了叫做 oh-my-openagent），这个插件我大概用了 2 个月，总体评价就是，它绝对是为 vibe-coding
而打造的，所以结果就是它非常得费 token 且行为非常得不可控。

所以你如果本身是程序员，且日常工作就是编程，**不推荐它** 。

我更推荐你装这个插件, [oh-my-opencode-
slim](https://link.zhihu.com/?target=https%3A//github.com/alvinunreal/oh-my-
opencode-slim)，它的作者认为 oh-my-opencode 的动机是好的，只是推行 vibe-coding
有很大的问题，所以他“取其精华去其糟粕”，做了这个插件。目前这个插件是我**推荐** 的，也认为是当下使用 opencode 做编程任务必装的插件之一。

* * *

oc 实际上我认为相比较 cc 最大的优点是它真正是做到了 open，从设计层面，就是面向所有的 model 而设计的，而 cc 从原生层面，仅支持
anthropic 的 models，除非你用 cc-router。这个事情，随着 model 越来越智能，越来越多样化，国内国外差距越来越小，oc
的优势就越明显。

咱就说从最基本的使用体验看，oc 原生直接使用各种 models，你还需要额外起个 cc-router，本身就给一般人增加了障碍，更别提什么
kyc、封号这些事情了。

而且当下的 ai coding，单单依靠某个模型已经落伍了，当下主流的模式已经趋近于 agent team，即不同的 model 去做自己擅长的
task，oc 配合 oh-my-opencode-slim 直接把这个开发体验拉到 max，同时又得益于国内 model 的 cost 普遍低于御三家的
model，可以说是两全其美了。

oc 另外一个优点是，它本身是按照 server client 这种架构来设计的，核心 agent 的部分，你可以一行命令 opencode serve
启动一个 http server，之后你就可以玩起来了。

往最简单说，你完全可以把它当作一个轻量级的 agent 内核，基于 api 调用将它包装为其他的 agent 或者是配合 chrome extension
做一些尝试，我在公司内部做了挺多类似的事情，效果都挺好的，你不说细节，大家都不知道 agent 的部分其实就是 oc 本体。

再来说下套餐。

oc 我之前一直是配合 glm-5 来用（偶尔用 qwen），多模态配合 kimi，套餐一开始直接用的智谱，后来实在是因为被 429
逼疯了，换到了百炼。再后来百炼停了 lite 和 pro 的套餐，正好 oc 官方又推出了 go，所以我就又切换到 go 了，到现在一直也是在订阅
go，可以说是非常的经济划算，费用基本和各大国内套餐的 lite 一档持平。

另一方面，[opencode-
go](https://link.zhihu.com/?target=https%3A//opencode.ai/go%3Fref%3DEXHCRPF6PS)
定期会更新很多免费模型，虽然有限额，但设置好合理的 fallback 规则可以尽情白漂。

* * *

除了 oh-my-opencode-slim，我还极力推荐这个插件 [@tarquinen/opencode-
dcp](https://link.zhihu.com/?target=https%3A//github.com/Opencode-
DCP/opencode-dynamic-context-pruning)，它实际上就是 dynamic-context-pruning
的实现而已。很多人对 DCP 嗤之以鼻可能是因为它会降低 input cache 命中率，但实际体验下来，最多只会降低 10% 到
15%，且你的任务越长，影响越小，为了刷 cache 命中率而放弃压缩上下文带来的优势，属于捡了芝麻丢了西瓜。

针对上下文优化，评论区（
[@米非](https://www.zhihu.com/people/2fa40b89c265bd1aa2e5b897f463339b) ）也推荐使用
[magic-
context](https://link.zhihu.com/?target=https%3A//github.com/cortexkit/magic-
context/tree/master) 这个插件，dcp 除了会降低 input cache
命中率之外，因为它会动态地、相对高频地改写你的上下文，确实偶尔会引发“降智”的现象，只是很少遇到，而且再近期使用 deepseek v4
之后，由于上下文够长，我刻意将针对 deepseek v4 的 dcp 关闭了。 magic-context 我最近也试用下看看，有什么感受再来更新。

updated:

最近试用了 magic-context 近两周的时间，长短任务都有尝试，总体上感觉在 model 上下文足够长的情况下，确实使用体验会比 dcp
更好，同时，随着 GLM-5.2 发布，它的上下文也是 1M，而且未来 GPT 也标榜自己的上下文长度会达到 1.5M，model
的上下文会越来越长，因此动态压缩的性价比会越来越低，而跨 session、跨仓库的动态记忆的性价比则会越来越高。

评论区的问题统一放到这里解答。

> 多模态配合Kimi这段，我用OC搭Kimi好像不能直接读取PDF，需要自己先对PDF预处理，是不是说明没有实现多模态啊？

多模态这块支不支持不看 oc，而是看 model，以及推理引擎的配置，实际上一般的 model provider 都是好用的，如果不好用可以试试下面的配置：

    
    
    "modalities": {
       "input": [
          "text",
          "image" // 这里会支持图片多模态
       ],
       "output": [
          "text"
       ]
    },

另外就是 options 的配置，会直接原封不动的把其中的 key-value 参数透传给推理引擎，如果上面的配置仍然不好用，就需要在 options
做文章了，不过因为情况比较杂，具体遇到哪种再说哪种吧。

> oh-my-opencode-slim 中的 Orchestrator 在 deepseek v4 下，总是不将任务 delegate 给
> subagent？

这个问题我确实在刚开始切换到 ds v4 时也有遇到，刚开始是以为出问题了，但后来发现并不是，它仍然会在一些场景下，将任务 delegate 出去，比如
design 或者 review 就会去找 Oracle，查文档是 Librarian 等。

如果任务没有被 delegate 出去，那就是 model 认为这个任务它自己就可以完美解决而不需要额外委托给 subagent，下面是源码中
Orchestrator 的 persona，可以发现，并没有包含类似 Must 或者 Always 的字眼：

> You are a workflow manager for coding work. Your job is to plan, schedule,
> delegate, monitor, reconcile, and verify specialist-agent work. You are not
> the default implementation worker.  
>  
> Optimize for quality, speed, cost, and reliability by dispatching the right
> specialist lanes, tracking background task state, and integrating terminal
> results into one coherent outcome.  
> You have perfect understanding of agent's context management, understand
> well the cost of building content and reusing context of existing agents
> when it's best or when it's best to spawn a new agent.

如果想要覆盖或者修改 Orchestrator 的 persona，可以直接在 opencode 的配置目录下，创建 oh-my-opencode-
slim/orchestrator.md
去覆盖它，详情[参考这里](https://link.zhihu.com/?target=https%3A//github.com/alvinunreal/oh-
my-opencode-slim/blob/master/docs/configuration.md%23prompt-overriding)。

还有一种方式就是使用 GLM-5 系作为 Orchestrator，会更符合理想中的模式。

updated:

因为最近 omo-slim v2 也更新了不少版本，感觉最大的亮点就是 async background task 吧，完全是基于 oc 目前已经实现的
asycn task tool_call 来实现的。

如果你高频地使用 oc 以及 omo-slim，可以发现这种非阻塞式的开发体验真得非常流畅。

什么叫非阻塞式？就是你只管创建任务就行，其余的 oc 和 omo-slim 会帮你解决：

  * A 依赖 B，没问题，B 会在 A 完成后才开始
  * A 和 B 毫无关联，直接并行 dispatch
  * A 开始运行，你又发布了一个包含一些更新逻辑的 A'，直接取消 A 再重新 dispatch A'
  * A 执行一般发生错误了，直接重试
  * ...

oc v2 版本也已经对会话管理进行了重写，未来这种开发体验会回归 oc 本体而非插件。
