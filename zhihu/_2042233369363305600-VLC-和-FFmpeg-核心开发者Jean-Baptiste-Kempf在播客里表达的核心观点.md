1\. 为什么读代码这么难?

他在对话里给出的理由很直接：

①代码是思考的压缩结果，不是思考过程本身。

你当时写代码时，脑子里有完整的问题场景、多种方案的权衡、临时的妥协、甚至是为了赶时间留下的“补丁”。这些思维过程，几乎不会完整地留在代码或注释里。

②即使自己写的，几个月后也读不懂。

他举了个例子：假设一个人在自己智力巅峰状态，写出了有生以来最棒的代码。六个月后，这个人再回头看，很可能已经看不懂了，因为“读代码比写代码更难”。

③读别人的代码更难。

别人写代码时的所有隐性知识（业务逻辑的由来、当时的外部约束、没写出来的设计决策），你完全没有，只能从代码字面上逆向推导。这种逆向工程非常耗费心力。

2\. 这个认知，和“不要轻易重写”直接挂钩

他在播客里说这话，是为了回应 Rust 社区部分人鼓吹的“用 Rust 重写一切”的思潮。

逻辑链条是这样的：

①新人接手一个复杂的 C 老项目，读不懂代码。

②因为读不懂，就觉得这代码写得很烂、应该重写（“这堆屎山，我来推倒重来，保证写得更好”）。

③于是开始用 Rust 或其他语言重写，比如重写 coreutils。

④很快达到 80% 的功能，似乎很顺利。

⑤剩下的 10%、最后的那 1%，却要花掉 99% 的时间——因为那些看似奇怪的代码，往往藏着多年积累的边界条件、罕见 bug 修复、平台兼容性等关键逻辑。

⑥这些“隐藏的智慧”，正是当初读不懂的部分，但重写时也不会自然被保留下来。

所以他的结论是：因为读代码极难，所以你以为自己看懂了需要重写，其实你根本没懂；而贸然重写，注定会丢失大量隐性知识，变成一个长期折磨人的半成品。

这也是他提到的 Elon Musk
那句话的意思：原型容易，造一辆真能大规模上路、不比燃油车差的电动车，难上无数倍。重写一个小工具的前80%功能，和做一个能完全取代旧系统的生产级软件，是完全不同量级的工程。

3\. 这个观点并不全盘否定 Rust

播客上下文里，他并没有说 Rust 不好，反而肯定了 Rust：

①做全新项目时，Rust 的内存安全、所有权模型，比 C++ 更善于管理内存，是非常好的工具。

②在 VLC 里也做过 Rust 模块的试验，技术上可行。

问题出在与现有大量 C/汇编代码互操作和社区“重写一切”的乌托邦倾向。

而且他还提了一个更根本的安全隐患：即使把 C 部分用 Rust
重写了，如果为了性能还要保留手写汇编，那内存安全模型就被打破了——因为手写汇编可以随意跳转内存。所以他觉得该做的不是简单的“用 Rust 替换
C”，而是去做“安全的汇编（编译器检查的汇编）”。

4\. 这个“读代码难”的困境，有没有解法？

他的核心关切不在于“重写”本身，而在于我们对现有代码的理解远远不够，却太快动手推翻。

如果要提炼出一些有建设性的方向，大概是：

①读代码是一种需要刻意训练的能力，不是会写就自然会读。

②重构优于重写：在保留现有逻辑的前提下，逐步改善结构，而不是推倒重来。

③把隐性知识显性化：强迫自己写清楚 why（为什么这么写，而不是做了什么），尤其是那些奇葩的边界处理。

④在做任何重写决策前，先回答：我真的完全理解原系统在极端情况下的全部行为吗?
