title: Android为什么不直接执行Linux的程序？而是自己搞一套？
type: archive-web

Android 自己搞一套，纯粹是生态问题，跟底层 C 库关系不大（甚至说没关系）。在此前 Linux
生态中基本没有为手机做适配的技术框架，即适合小屏幕全屏使用，纯触摸交互的框架。

所以 Android 要开发自己的一套框架，这是必然的。否则开发者开发的东西，能在手机上运行，却完全无法正确的显示布局，完全无法交互，有什么用？你现在用
x86 的 Windows 平板，去体验一下旧的 win32 应用，什么感觉。你再想想把平板尺寸缩小到手机大小，还能用吗？

所以在 Linux
软件生态没有进入手机领域之前，自己设计一套开发框架是必须要做的前提。然后开发者基于你的框架开发的应用，就自然而然、老老实实的符合你的规范但不再“原生”。现在你又抱怨怎么不直接执行
Linux 程序？传统 Linux 程序压根就没适配你手机啊。

我们假想一下，在手机中直接用 Linux 软件的场景：尼玛的字体怎么那么小啊，这 UI
布局严重不合理、显示也不全啊，怎么滚都滚动不了啊，卧槽怎么输入起来都这么麻烦。然后你去人家开发者那里反馈问题，人家一脸问号，我 TM
给桌面设计的软件，你在手机上用出的问题关我吊事儿。

然后才是技术问题。在底层 Android 虽然继承了 Linux 的很多特性，但它却不怎么利用 GNU 生态，桌面 Linux 生态的技术，包括
[http://X.Org](https://link.zhihu.com/?target=http%3A//X.Org)，Wayland
这些重要的图形协议。Android 使用自己的图形系统。也就是说 Linux 原生的 GUI 程序大多就不能在 Android
上运行，因为它们的底层图形技术不支持 Android 的显示系统（SurfaceFlinger）。这也证明了从一开始 Android 就不在意 Linux
的软件生态。

技术方面和 C 库没有关系，概念上也无关。实际上 Android 的软件生态中是大量使用原生库的，这些 C/C++ 代码只是换上面向 Android
的工具链编译而已。把其它在桌面 Linux 流行的程序用这个思路重新编译，它依然是原生 LInux 程序，只是不见得能在 Android
中正确运行和使用。命令行程序没有这个问题，所以命令行程序普遍能作为「直接执行的 Linux 程序」这个身份在 Android 上使用。我用 Rust
写过的几乎所有命令行软件都在 Android 中部署使用过。

在技术层面 Android 是一个和常规桌面 Linux 有重大区别的系统（虽然它们本质相同），Android 多了很多自己的机制。例如 Android
的应用有自己的生命周期，所有 Android 软件都要在生命周期的恰当时机做一些事情，让自己在被回收后能恢复状态，甚至避免数据丢失。但这些在原生 Linux
程序中不存在，你把它们运行在 Android 中，就是不安全的。

此外目前的手机系统和 PC 操作系统的一个重大区别是：手机系统把开发者限制在自己的条条框框当中，而 PC 操作系统则极为自由。这是普遍的，而不是只有
Android 才这样。

总结就是 Android 这种为手机设计的系统，在生态层面和 Linux 差异太大，直接运行 Linux 程序并不能享受到 Linux
的软件生态（一堆跑起来没法用的东西，纳进来干嘛？）。技术方面 Android 有许多自己的条条框框，它限制了开发者不能太自由，但也让应用具统一的 UI
效果和交互逻辑（不包括游戏，游戏我抽空另说）。

KDE 桌面
