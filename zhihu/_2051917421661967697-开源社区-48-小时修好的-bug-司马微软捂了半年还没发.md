方案是把私钥的关键部分锁在 TPM 芯片里——拿到文件也没用，离开这台设备的硬件，它就是一堆乱码。安全性直接跃升一个数量级。

* * *

**1 蜜月期：Windows Hello 是怎么变成「穷人版 YubiKey」的**

很多人对 SSH 密钥的认知还停留在 `ssh-keygen -t rsa` 的时代——本地生成一个私钥文件，放在 `.ssh` 目录下，用就完了。

但这个方案的致命缺陷是：私钥文件可以被复制。如果你的电脑被入侵，或者你不小心把私钥传到了某个共享目录，攻击者拿到文件就能冒充你。

OpenSSH 从 8.2 版本开始，给了一个新答案：FIDO/U2F 硬件认证器。新增了两种密钥类型——

  * `ecdsa-sk`：基于 NIST P-256 椭圆曲线 + 物理安全密钥
  * `ed25519-sk`：基于 Ed25519 曲线 + 物理安全密钥

“-sk” 后缀代表 security key。它们的核心逻辑是：**私钥的关键部分根本不完整存储在硬盘上，每次签名操作都必须由硬件安全密钥（或 TPM
芯片）参与授权** 。这意味着即使有人偷走了你的私钥文件，没有你的物理设备，他连门都摸不到。

这个安全等级，基本就是高性能军用级别了。但问题在于——你上哪儿买安全密钥去？一个 YubiKey 动辄几百块。

微软在这里做了一件很聪明的事：把 Windows 11 内置的 **TPM 2.0 芯片 + Windows Hello** （PIN / 指纹 /
人脸识别）伪装成一个 FIDO 安全密钥。

简单来说就是——你不需要花一分钱买额外硬件，只要你的电脑有 TPM 2.0（2016 年以后的商务本基本都有），你的指纹识别器就能变成一个「免费的
YubiKey」。

从 OpenSSH for Windows 8.9 版本开始，这个功能就可以正常使用了。你只需要在 PowerShell 里敲一行：

    
    
    ssh-keygen -t ecdsa-sk

系统会弹出 Windows Hello 的指纹或人脸验证窗口，你按下手指，一个与设备 TPM 硬绑定的 SSH
密钥就生成了。私钥文件虽然在磁盘上，但离开了这台设备的 TPM，它就是一堆毫无意义的乱码。

这个体验有多好呢？对于开发者来说，你不需要额外记密码，不需要买硬件，不需要学任何新概念——手指一按，密钥生成，服务器登录，丝般顺滑。

看起来，这不是完美的安全方案吗？

但问题在于——

**2 灾难降临：2025 年 10 月，蜜月戛然而止**

从 2025 年 10 月开始，大量 Windows 11 用户发现，原本丝般顺滑的流程，突然全部崩了。

Microsoft Q&A 上有一位用户详细描述了症状：

> 操作系统：26200.6901 PC：ThinkPad T14s  
>  `ssh-keygen -t ecdsa-sk` 可以弹出指纹验证窗口，按完指纹后密钥也确实生成了。  
>  但用 `ssh` 登录远程机器时，只弹出「选择通行密钥」对话框——里面有「iPhone、iPad 或 Android
> 设备」和「安全密钥」两个选项，**就是没有使用 Windows Hello 指纹的选项** 。  
>  这个问题大概从 2025 年 10 月开始出现。在那之前，一切正常。

注意他的关键词——「在那之前，一切正常」。

这是一个「明明一直好着，突然就坏了」的功能。这种类型的故障，比一开始就坏的故障更让人崩溃——因为你已经把它纳入了你的工作流，你的服务器只允许硬件密钥登录，你的所有自动化脚本都绑定了这个机制。

然后有一天，它突然告诉你：不好意思不行了。

更离谱的是，受伤的不止 Windows Hello 用户。微软在 2024 年 10 月推送的累积更新 **KB5044273** ，在更新 OpenSSH
组件的同时，直接导致了 **YubiKey 的 PIV/PKCS11 证书识别功能失效** 。对，连物理安全密钥的「原住民」都被误伤了。大量 YubiKey
用户在 Windows Terminal 和 VSCode 里无法进行身份验证。

**3 追根溯源：到底是谁的锅？**

那么问题来了——到底是什么原因，让一个稳定运行了很长时间的功能，说崩就崩？

要理解这个问题，需要先搞清楚 FIDO 协议里的一个小概念：**认证（Attestation）** 。

当安全密钥生成一对新密钥时，它可以额外返回一份「认证数据」。这份数据能证明两件事：

  1. 这个密钥确实是在一个合法的、经过认证的硬件安全密钥上生成的（不是软件模拟的假密钥）
  2. 这个安全密钥通过了某种行业认证级别（比如 FIDO Level 1 或 Level 2）

对于银行、军工等高安全场景，认证数据是强制要求的——「你必须用通过 FIDO Level 2
认证的硬件，否则不认」。这就像你去某些地方办手续，必须用二代身份证，一代身份证就是不行。

但对于普通开发者来说，这个认证数据其实可有可无——我只需要「密钥跟硬件绑定」这个事实，至于这个硬件有没有通过行业协会的认证，我根本不关心。

然而，OpenSSH 的 `ssh-keygen` 在生成 `ecdsa-sk` 密钥时，**默认行为是要求安全密钥必须提供认证数据** 。你不提供，我就报
`invalid format` 给你看。

与此同时，Windows Hello 这边发生了什么事呢？

根据开发者 `michael-dev` 在 OpenSSH Bug 3761 中的分析：

> Windows Hello 在大约 2025 年 10 月移除了对 attestation 的支持。这可能是因为 Windows Hello
> 正在为后续支持「通行密钥」（Passkey）做准备，改变了底层 API 的行为。

翻译成人话就是：微软的 Windows Hello 团队为了迭代新功能，悄悄改了 API——你的安全密钥不再返回认证数据了。

于是，一个经典的「两头都对，中间死掉」的局面出现了：

  * Windows Hello 说：我不给认证数据了，这是我的权利，我在为 Passkey 铺路。
  * OpenSSH 说：你不给我认证数据？那你就是不合法，报错！
  * 用户说：？？？

从协议层面看，两边都没犯根本性的错误。Windows Hello 移除 attestation 支持不是 bug，是设计决策。OpenSSH 默认要求
attestation 也不是 bug，是 FIDO 标准行为。

真正的问题是：**OpenSSH 没有处理「安全密钥不支持 attestation」这种边缘情况** 。当 Windows Hello
说「我不提供这个」时，OpenSSH 应该优雅地降级——拿不到认证数据就不拿，密钥照样生成，安全等级稍微降一点但照样能用。而不是直接崩溃给你看。

但这就是软件工程的残酷现实：你永远想不到下游的 API 会在什么时候、因为什么原因突然改变行为。

**4 开源的速度：48 小时**

2024 年 12 月 2 日——注意这个日期，它比大规模用户感知到故障早了将近 10 个月——开发者 `michael-dev` 在 OpenSSH
的官方 Bugzilla 上提交了 **Bug 3761** 。

他在报告中精准地切入了问题要害：

  1. `ssh-keygen` 在处理不支持 attestation 的安全密钥时会直接失败
  2. Windows 11 的 Windows Hello 安全密钥就是一个活生生的典型例子
  3. 这个问题导致了 GitHub 上 Win32-OpenSSH 的多个 issue（#2040 和 #2279）
  4. 之前能用，说明 Windows Hello 是近期才移除的 attestation 支持
  5. 根据 libfido2（YubiKey 团队维护的底层 FIDO 库）的 Issue #840，对于 “none” 类型的 attestation，根本不应该调用 `fido_cred_verify_self`

关键是第五条——他不仅报告了问题，还追溯到了底层依赖库的既有讨论，并且直接提交了一个补丁。

不到 24 小时。

2024 年 12 月 3 日，OpenSSH 核心维护者 **Damien Miller** 响应了。补丁被审查、通过、合并到 OpenSSH
主分支。Bug 3761 的状态从 “NEW” 变成了 **“FIXED”** 。

从报告到修复，全程不到 48 小时。

这就是开源社区的速度。没有工单流转，没有部门审批，没有发布排期，没有「已转交相关团队处理」——一个开发者发现问题，定位根因，写补丁，另一个维护者审核合并，完事。

如果你了解企业软件开发的节奏，你应该知道，48 小时在大多数公司里甚至不够走完「确认这是一个
bug」的流程。但问题来了：上游修了，不代表下游拿到了。开源的速度再快，也快不过商业公司的发布排期表。

**5 微软的迷之操作：修复在哪里？**

上游修了。然后呢？

这里需要搞清楚微软这边的两个仓库：

仓库| 定位| 状态  
---|---|---  
PowerShell/openssh-portable| 微软的开发仓库，代码修改都在这里| 非常活跃，最新提交就在几天前  
PowerShell/Win32-OpenSSH| 微软的发布仓库，用户能下载到安装包的地方| 发布频率极低  
  
用户在 `Win32-OpenSSH` 的 Releases 页面能下载到的最新版本，是 2025 年 10 月发布的。这个版本的 `ssh.exe`
文件日期显示为 2025 年 10 月，版本号写着 `OpenSSH_for_Windows_10.0p2`。

这个版本包含 Bug 3761 的修复吗？从 Release Notes 来看，它说包含了 OpenSSH 10.0p2 的上游更改，而 Bug 3761
正是 10.0 的一部分。但实际测试结果告诉我们——要么补丁在合入过程中被遗漏了，要么合入了但在 Windows
的特定构建环境下没有生效。无论哪种情况，结果都是同一个：用户拿到的版本，不 work。

  

更让人窒息的是，微软在 2025 年 10 月还推送了另一个累积更新 **KB5066835**
，引入了更严格的加密策略，进一步影响了虚拟和物理智能卡（包括 Windows Hello）。这个更新让情况雪上加霜——即便将来 OpenSSH 修好了
attestation 兼容问题，新的加密策略可能又会制造出新的障碍。

发现没有？微软内部的 Windows Hello 团队、加密策略团队、OpenSSH 打包团队，这三个部门之间似乎完全没有协调。一个团队改了
API，另一个团队收紧加密策略，第三个团队不跟上修修复——三股力量拧在一起，最终的结果就是用户被夹在中间反复碾压。

**6 第三方的自救：花了两年的力，挡不住底层的一刀**

社区开发者也不是没试过自救。

`tavrez/openssh-sk-winhello` 就是一个典型的第三方「桥梁」工具。它的思路很直接：让 OpenSSH 绕过内置的 FIDO
协议栈，直接通过 Windows 原生 Hello API 来跟 TPM 沟通。

使用方式很简单：

    
    
    ssh-keygen -t ecdsa-sk -w winhello.dll

或者设置环境变量：

    
    
    $env:SSH_SK_PROVIDER="winhello.dll"
    ssh-keygen -t ecdsa-sk

这个工具 2020 年就发布了 v2.0.0，支持 OpenSSH 8.4 及以上版本，一直兢兢业业地当着那道「桥梁」。

但问题在于——

它本质上还是在调用 Windows Hello 的底层 API。当微软在 2025 年 10 月把 attestation 支持从 API
层直接移除后，任何上层的「桥梁」都无法凭空变出已经不存在的功能。你可以把桥修得再漂亮，河都干了，船也没法走了。

所以用户在使用这个第三方工具后，依然会看到一模一样的报错：`Key enrollment failed: invalid format`。

这就是第三方工具最无奈的地方——你花了几年时间打磨一个解决方案，底层 API 一个静默变更，你连抢救的机会都没有。

**7 时间线：2024 到 2026，一段荒诞的半年**

时间| 事件  
---|---  
2024-10-08| 微软推送 KB5044273 累积更新，OpenSSH 升级到 9.5p1，同时导致 YubiKey PIV/PKCS11 失效  
2024-12-02| michael-dev 在 OpenSSH Bugzilla 提交 Bug 3761，附带补丁  
2024-12-03| Damien Miller 合并修复补丁到 OpenSSH 主分支——48 小时内完成  
2025-10 前后| Windows Hello 移除 attestation 支持，功能失效被大规模用户感知  
2025-10| 微软发布 OpenSSH_for_Windows_10.0p2（基于修复前的代码快照）  
2025-10| 微软推送 KB5066835，进一步收紧加密策略，雪上加霜  
2026 年至今| 用户仍在等待包含修复的官方版本  
  
发现没有？2024 年 12 月修好的东西，到了 2026 年还没进发布渠道，这就是一个纯粹的流程问题。

开源侧：48 小时。商业侧：半年起步。

**8 算账：谁该为这场灾难买单？**

**微软：流程僵化，罪魁祸首。**

这是微软整个发布体系的系统性问题。开发仓库（`openssh-portable`）热火朝天，发布仓库（`Win32-OpenSSH`）死气沉沉。明知
Windows Hello 移除了 attestation，却没有内部预警，没有快速响应机制，甚至没有人在发布前跑一轮回归测试——否则一个 `ssh-
keygen -t ecdsa-sk` 就能立刻暴露问题。

KB5066835 的加密策略变更进一步加剧了问题，说明微软内部的不同团队（Windows Hello 团队、安全策略团队、OpenSSH
打包团队）之间完全缺乏协调。微软不是没有资源，而是资源被各自为政的部门墙切碎了。

**OpenSSH 上游：反应迅速，无可指摘。**

从 Bug 报告到补丁合并，不到 48 小时。开源社区的速度和效率，放在任何商业公司的对标场景里，都是碾压级别。

**YubiKey（Yubico）：纯属躺枪。**

没有任何证据表明 YubiKey 阻挠了任何补丁。恰恰相反：补丁的灵感来源之一，正是 YubiKey 团队维护的 `libfido2` 库的 Issue
#840。KB5044273 更新同样导致 YubiKey 用户无法正常工作。YubiKey 用户和 Windows Hello
用户在这个事件里是「难兄难弟」，都是被微软的流程问题拖累的受害者。

那么，用户呢？

用户在 Reddit、Microsoft Q&A、GitHub Issues
上反复发帖询问，得到的只有机器人的自动回复、其他用户的「我也是」、以及一些零零星星的临时 workaround（卸载
KB5044273？可以，但你的系统安全补丁也没了）。没有官方公告，没有时间表，没有哪怕一句「我们知道了，正在处理」。

这就是微软对开发者用户的真实态度。

**9 深层反思：开源与商业的「节奏脱节」**

这件事的本质是什么？

不是「微软技术不行」，也不是「开源社区就是比商业公司强」这种简单的二元对立。这件事的本质，是**两种完全不同的软件交付节奏** 之间的激烈碰撞。

开源侧：发现问题 → 定位根因 → 提交补丁 → 审核合并 → 发布。这个链条在 OpenSSH 这边跑了不到 48
小时。开源社区的运作逻辑是：代码就是一切，谁有本事谁修，修了就合，合了就发。

商业侧：用户反馈 → 工单系统 → 指派团队 → 内部复现 → 排入迭代 → 代码修改 → 测试验证 → 合规审查 → 发布排期 →
推送。这个链条在微软这边跑了大半年还没跑完。

当一个操作系统级别的核心组件（OpenSSH on Windows）依赖一个快速迭代的开源上游（OpenSSH
Portable），而下游整合方（微软）的发布周期以「月」甚至「年」为单位时，这种脱节就是必然的。

更致命的是，微软似乎不认为这是一个需要紧急处理的问题。`Win32-OpenSSH` 仓库的活跃开发早已转移到别处，而用户能接触到的发布渠道，依然停留在
2025 年 10 月的那个有缺陷版本上。
