## 方案一、git-filter-repo 修改历史

缺点：需要所有人重新clone，不能直接pull，否则前功尽弃

## 1.1 安装

    
    
    pip install git-filter-repo

## 1.2 分析

    * 在根目录执行 

    
    
    git filter-repo --analyze

    * 生成分析报告在 .git\filter-repo\analysis 目录下

![](https://pic2.zhimg.com/v2-956c6d6f4583431ab5360697ac66f84d_1440w.jpg)

## 1.3 处理

    * extensions-all-sizes.txt (优先看这个) 按**文件后缀名** 统计的占用空间
    * path-all-sizes.txt (其次看这个)按**具体路径/文件** 统计的累计占用空间（包含历史版本）。
    * blob-shas-and-paths.txt 按文件大小排序
    * directories-all-sizes 按目录大小排序
    * **path-deleted-sizes.txt** 统计那些**已经被删除但仍留在历史记录中** 占空间的文件。这是优化的“肥肉”，删掉它们不会影响当前项目运行。
    * **renames.txt** 记录了历史上的重命名操作。由于 Git 跟踪的是内容，重命名有时会导致统计上的混淆，这个文件帮你溯源。
    * 比如这个，有大聪明把unity的ios安装包上传到项目内，虽然后面删掉了，但是还保留在历史里，文件大小就这样变大了

## 1.4 实战

**嗯，很慢，一个早上没了，还是直接大批量处理吧**

    * 处理完结果，跟预期不大一致，148=》142，预期是147.5GB

![](https://pic3.zhimg.com/v2-463d9ee5211b0b603fc60045869bedba_1440w.jpg)

### 1.4.2 按类型删除： 到 extensions-all-sizes.txt 找后缀名

    
    
    # 2. 批量剔除特定的巨型二进制资产 (示例为常见游戏冗余文件)
    # --invert-paths 表示删除路径，--path 指向具体后缀或目录
    git filter-repo \
      --path-glob "*.hdr" \
      --path-glob "*.png" \
      --path-glob "*.exr" \
      --path-glob "*.asset" \
      --path-glob "*.mesh" \
      --path-glob "*.unity" \
      --path-glob "*.fbx" \
      --path-glob "*.FBX" \
      --path-glob "*.lightmap" \
      --path-glob "*.bak" \
      --path-glob "*.lz4" \
      --path-glob "*.exe" \
      --path-glob "*.obj" \
      --invert-paths --force

![](https://pic3.zhimg.com/v2-c21d4232f119e9a48ae4e3fa7e0734b4_1440w.jpg)

效果是明显，142==》7GB了

### 1.4.3 按文件大小清理

    
    
    # 3. 如果你想删除所有超过 50MB 的历史文件（最暴力但也最有效）
    # git filter-repo --blob-size-limit 50M --force

  * 在执行完 `filter-repo` 后，Git 的底层对象可能还未完全释放。请依次执行以下命令来强制回收磁盘空间：

    
    
    # 解除所有引用并清理过期 log
    git reflog expire --expire=now --all
    
    # 强力垃圾回收，重新打包对象（这个过程可能较慢，但能极大减小 .git 体积）
    git gc --prune=now --aggressive

### 1.4.4 按时间截断历史

找到半年前（或一年前）那个时间点对应的 **Commit Hash**

    
    
    # 查找 6 个月前最后一次提交的 Hash
    git log -1 --before="6 months ago" --format=%H

使用 --refs 限制范围

    
    
    # 假设 abc12345 是半年前的提交
    git filter-repo --refs abc12345..HEAD
    注意：这会删除 abc12345 之前的所有历史，让该提交变成仓库的“根提交”（Initial Commit）。

## 三、Git LFS 的原理

## 3.1 Git LFS 的原理：化整为零

在传统的 Git 中，当你修改一个 100MB 的文件并提交时，Git 会把这个文件的完整副本存入 `.git` 目录。随着版本更迭，`.git`
会迅速堆积成百上千个巨型文件。

**Git LFS 的核心逻辑是“偷梁换柱”：**

  1. **本地仓库（.git）** ：不再存储真实的大文件内容，而是存储一个只有几百字节的 **Pointer File（指针文件）** 。这个文件记录了真实文件的 ID (SHA-256) 和大小。
  2. **LFS 服务器** ：真实的大文件被上传到专门的 LFS 存储区。
  3. **工作区（Working Copy）** ：当你切换分支或 `checkout` 时，LFS 插件会自动根据指针文件，从服务器下载对应的真实文件替换到你的文件夹里。

建议根据 `extensions-all-sizes.txt` 报告中的高占用后缀进行设置。

    
    
    git lfs track "*.unity"
    git lfs track "*.prefab"
    git lfs track "*.asset"
    git lfs track "*.fbx"
    git lfs track "*.exr"
    git lfs track "*.png"

**注意** ：运行完这些命令后，根目录会生成一个 `.gitattributes` 文件。**必须把这个文件提交到 Git**

### 3.3 团队协作建议

  * **安装 LFS 客户端** ：确保团队所有成员都安装了 Git LFS 扩展，否则他们拉下来的大文件只是几个字节的文本（指针）。
  * **锁定机制（File Locking）** ：对于 `.unity` 这种无法合并的二进制场景文件，可以开启 LFS 的锁定功能，防止两个人同时修改：

    
    
    git lfs track "*.unity" --lockable

  

项目用的自建的gitLab，git lfs是免费的，那就直接把scene仓重启，添加上git lfs属性就好了。

### 3.4 给服务器管理员的配置清单 (必做)

默认的 GitLab 配置是针对代码（文本）优化的，直接传几个 GB 的 LFS 大文件很容易失败。请把这份清单转给负责维护 GitLab 的同事：

### A. 修改存储路径 (防止系统盘爆满)

默认情况下，GitLab 把 LFS 对象存放在 `/var/opt/gitlab/gitlab-rails/shared/lfs-
objects`。如果这在系统盘（root分区），很快就会爆满导致 GitLab 宕机。

**操作** ：在 `/etc/gitlab/gitlab.rb` 中修改存储路径，指向那块大容量的数据盘。

    
    
    # /etc/gitlab/gitlab.rb
    
    # 开启 LFS
    gitlab_rails['lfs_enabled'] = true
    
    # 将存储路径指向挂载的大硬盘 (例如 /mnt/data)
    gitlab_rails['lfs_storage_path'] = "/mnt/data/gitlab-lfs"

### B. 调整超时限制 (防止上传中断)

美术上传一个 2GB 的 `.psd` 或 `.unitypackage` 可能需要几分钟。默认的 Nginx 设置可能会判定连接超时并切断。

**操作** ：增加超时时间和最大包体限制。

    
    
    # /etc/gitlab/gitlab.rb
    
    # 允许最大上传大小 (根据需求设大点，例如 5GB)
    nginx['client_max_body_size'] = "5120m"
    
    # 增加 Git HTTP 请求的超时时间 (例如 1小时)
    gitlab_rails['git_http_server_write_timeout'] = 3600
    gitlab_rails['git_http_server_read_timeout'] = 3600

修改完配置后记得运行 `sudo gitlab-ctl reconfigure` 和 `sudo gitlab-ctl restart`。

### C. 未来的隐患：垃圾回收 (GC)

Git LFS 的一个特性是：**它极其“贪婪”，只进不出。** 当你删除了某个大文件的引用，GitLab 服务器端的 LFS 文件**默认是不会删除的**
（为了防止误删）。

**长期维护策略** ： 如果一年后你们发现服务器硬盘快满了，需要管理员手动运行清理命令，删除那些“没有任何 Commit 引用”的游离 LFS 对象：

    
    
    # 在 GitLab 服务器上运行
    sudo gitlab-rake gitlab:cleanup:orphan_lfs_file_references
    sudo gitlab-rake gitlab:cleanup:orphan_lfs_objects
