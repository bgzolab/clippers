## **先看效果**

在说怎么做的之前，先看看成品是什么样子。把 smb.efi（一个约 250KB 的单文件）放进 QEMU 虚拟机的 UEFI Shell
目录，启动后自动进入游戏：

  * 完整 SMB1 游戏逻辑——32 个关卡，8 个世界，全部敌人、道具、隐藏砖块、管道、藤蔓
  * 256×240 NES 原生分辨率，经整数缩放自适应屏幕（在 1280×800 上为 3×，即 768×720 显示区域）
  * 双缓冲渲染，画面无撕裂
  * 方向键移动，1 或 / 键跳跃，2 或 . 键加速/发火球，Enter 开始，Space 选择

![](https://pic4.zhimg.com/v2-54cab2857f4e6db4c214e628a79eb4c7_1440w.jpg)熟悉的欢迎界面![](https://pic3.zhimg.com/v2-f692d1037b78f0b954ab0475485c590c_1440w.jpg)剩余人口画面![](https://pic1.zhimg.com/v2-9733e76b7534e80b61db872d9bf40d10_1440w.gif)电脑玩，和我的一个拙劣的表演。电脑键盘确实没手柄好用

这个项目从零到跑通，一共用了两个多小时。成本：DeepSeek V4 Pro 的 API 费用，5.2 元人民币。代码已经全部整理好，GitHub
地址在文章末尾。

## **AI辅助编程降低了创意门槛**

说实话，移植一个红白机游戏到 UEFI Shell
这种事，如果放在三年前，绝对不是一个人花一个周末能搞定的事情。在我的上上加公司，我一个花了一个月才将ffmepg移植到了某PDA项目中（说实话有点摸鱼），j2me的引擎也大概花了同样多的时间。

要移植这个游戏，你需要懂 NES 的 PPU 渲染管线——OAM 精灵表、CHR-ROM 图案表、调色板索引；你需要懂 UEFI 的 GOP
图形协议——帧缓冲的物理地址映射、BGRA 像素格式、PixelsPerScanLine 跨距；你需要懂 NES 6502 汇编到 C
代码的反编译逻辑——PRG-ROM 数据表的 ROM 地址宏、游戏模式跳转树、NMI 中断调度流程；你还需要搞定从 SDL 前端到 UEFI
前端的完整替换——渲染回调、输入轮询、帧率控制。

这还没算上 MSVC 编译器的 UEFI 目标适配——/SUBSYSTEM:EFI_APPLICATION、/NODEFAULTLIB、禁用 C++ 异常和
RTTI——以及 QEMU + OVMF 的调试环境搭建。

单独拎出任一项，都够折腾半天的。而 AI
辅助编程把所有这些“门槛知识”变成了可以在几分钟内通过对话获取的信息。当知识的获取成本趋近于零，行动力就成了唯一的变量。所以这次，我没光想，就直接上手了。

## **代码来源与我的改进**

这个项目的游戏逻辑来自 GitHub 上的 [nukep/smb-vanilla-
port](https://link.zhihu.com/?target=https%3A//github.com/nukep/smb-vanilla-
port)——一位开发者把 NES 上《超级马力欧兄弟》的 6502 汇编反编译成了 C 代码，总共约 11,732
行核心游戏逻辑。这份反编译代码保留了原版游戏的全部行为，包括那些经典的“Bug”（比如负世界管道）。

AI做的事情是把它从 SDL 窗口移植到 UEFI Shell 环境。具体改动包括：

  * UEFI GOP 渲染器：AI完全重写。从零实现了一套最小化 UEFI 类型定义（不依赖 EDK2 或 gnu-efi SDK），基于 GOP 帧缓冲的双缓冲软件渲染器，带整数 nearest-neighbor 缩放。
  * 非阻塞键盘输入：UEFI 的 SimpleTextIn 协议读取按键会阻塞。AI用定时器 + WaitForEvent 机制实现了真正的非阻塞轮询，同时发现 QEMU SDL 不转发字母键（Z/X/J/K 全部被拦截），最终改用数字键和符号键映射。
  * ROM 数据与版权分离：原始项目需要用户提供 .nes ROM 文件，包含 16 字节的 iNES 版权头。**我让它把 PRG-ROM（32KB 数据表）和 CHR-ROM（8KB 图案表）从 .nes 中剥离为独立的 .bin 文件，编译时嵌入。代码仓库不再含有任何任天堂的版权数据** 。这是我明确让它做的
  * 串口调试系统：AI使用 x86 I/O 端口直接写 COM1（0x3F8），通过 QEMU 的 -serial stdio 实时输出帧计数和按键事件，调试效率极高。当然，这个能力来自我写的Skill：

[https://github.com/MikeWuPing/emulator-uefi-shell-
app](https://link.zhihu.com/?target=https%3A//github.com/MikeWuPing/emulator-
uefi-shell-app)

## **DeepSeek 帮我修了一个隐蔽的渲染 Bug**

这里要特别提一下 DeepSeek V4 Pro 在代码改进上的贡献。

游戏中马里奥的精灵渲染有一个水平翻转逻辑——向左走的时候，马里奥的身体部件需要做像素镜像。SDL
原版的渲染器里，翻转是通过原始像素坐标索引瓦片数据来实现的。而我的第一版 UEFI
渲染器写成了用翻转后的坐标同时做瓦片索引和屏幕定位。结果就是：马里奥一转身，脸就跑到了身体后面，看起来像头身分离的怪物。

DeepSeek 在这个问题上给了我关键的提示——指出了瓦片数据索引应该使用翻转前的行列坐标，而不是翻转后的。改了那一行之后，马里奥终于正常了。这个 Bug
的根因本质上只有三行代码的差异，花了一点时间，关键是这个bug的fix是我和AI的一个交互式修改bug的过程：AI加入调试信息，打开QEMU，让我左走几下，它监控串口，看看数据是否正常。另外一个原因，是DeepSeek
V4 Pro还不支持多模态，以后加上了应该会方便很多。

## **花絮：我同时开了四个 Claude Code 窗口，四个方案都在跑**

其实今天我并不是只搞了这一个移植。我同时开了四个 Claude Code 终端窗口——相当于让四个 AI 开发小组并行工作，每个窗口对应 GitHub

  2. 一个 3D 的《超级玛丽 64》移植（已经可以运行，渲染有些问题还需要修）

  4. 还有一个完全Clean的版本，也跑通了，就是界面不是原生的，有点丑。

大家如果对 3D 马力欧 64 的 UEFI 移植或者其他版本感兴趣，在评论区留言。人多的话，我陆续把它们也开源出来。

## **开源的代价**

移植完成后，我去网上搜了一下。确实有人展示过在 UEFI Shell 下运行超级玛丽——YouTube 上有几个视频，BIOS 圈子里也有人提过这个
idea——但没有找到开源的。

我猜测原因很简单：在 AI 辅助编程成熟之前，这种跨领域的移植工作技术门槛确实不低。你要同时熟悉 NES 图形学、UEFI 固件编程、交叉编译工具链和
QEMU 调试。一个人从头搞，没个一两周下不来。花这么大成本做出来的东西，开源确实需要一点“舍”的勇气。

但在我这里，总成本是：2 小时 + 5.2 元 API 费。中间我还去睡了一觉。这个成本低到我没有理由不把它开源出来。
