**@广陵止息：** 我们在 4 月 13 日的[早报](https://sspai.com/post/108568)中详细介绍了 Windows
预览体验计划的新变化，总体来看是好事，所以这里就不再赘述了。在本期具透 Plus 中我想聊聊 Windows、macOS 和 Linux
发行版的测试版逻辑。并聊聊系统测试版的本质到底是什么？

![](https://cdnfile.sspai.com/2026/04/15/article/38b2dd3d859f181515d72e5ea1a27144.png?imageView2/2/w/1120/q/90/interlace/1/ignore-

我认为一直以来 Windows 的预览体验计划是带有一定营销性质的。Windows Insider 官网的表述一直包含「抢先体验」「与 Windows
预览体验成员团队和社区联系」「影响未来」「幕后揭秘」这样的说法，也就是把参加 Windows 内测的用户定义成社区内的一员。虽然 Insider
注册流程中有提及测试版中的风险，但这些信息远不够显眼，加上整体的宣传导向，我认为这种策略已经超出系统测试应有的范畴。

而且 Windows 以前特别喜欢分批推送，也就是同一个测试频道、同一个测试构建号的用户不一定能用上同一个功能。结果就是我一定要从社交媒体上才能知道
Windows 的新特性，然后再等到微软官方发了相关博客、不少外媒也已经写了新闻，而我还要用第三方的 vivetool
去打开这个开关才有。次数多了，这种信息差难免让人怀疑微软是否有意借此制造多轮传播效果。好在，微软在这次公告里也承认分批推送是 Insider
问题里比较失败的一部份。未来同一个频道、同一个版本的用户可以体验到一致的功能，这样可以提高提高测试一致性。

当然，Windows 最摸不着头脑的还是一大串测试渠道，Canary、Dev、Beta、Release
Preview，名义上是风险等级和稳定性的区别。理论上多频道可以对应不同开发阶段、不同变更幅度、不同回滚预期和不同目标测试人群，这在大型平台软件里不是完全没道理。

但 Windows
过去的问题在于，这套分层并没有稳定、透明地对应到用户的实际体验。在分批推送和功能开关的双重作用下，频道名义上的层级与真实的测试内容经常脱节，频道数量多反而成了负担，所以才让整个体系显得混乱。

作为对比，Apple 的测试版体系在风险告知方面做得更加明确。Apple 明确表示：「仅将 Beta
版软件安装在与商业运作无关的非生产设备上」。从渠道的角度来说，Apple 测试版只分为开发者测试版和公开测试版 2
个版本，通常开发者测试版会先发布几个版本，修了严重影响体验的 BUG 以后就会同步发布公开测试版。在功能体验方面，Apple
也习惯把新功能随系统一起推出。Apple 还为测试版准备了一份相当完整的已知问题说明文档，虽然一般人也不会看，但至少为测试者提供了必要的参考。

不过，Apple 的测试体系也并非没有问题。随着 Apple
向所有用户免费开放开发者测试版，开发者测试版和公开测试版的边界也在模糊。只是整体而言，Apple 在频道划分的简洁性和风险提示的明确性上确实比过去的
Windows Insider 做得更到位。

不同 Linux
发行版的测试机制并不相同，但很多发行版都以软件包仓库为基础：新软件包或更新会先进入风险更高的开发、测试或候选仓库，经过一段时间的集成验证、自动化测试、用户反馈或人工审核后，再进入面向普通用户的稳定仓库。不过，部分发行版也更强调整体验证后，按照系统快照发布，而不只是单个软件包在仓库之间逐级移动。

至于 Linux Kernel 的测试版基本只和开发者有关，普通用户很少会直接接触上游内核社区发布的测试版本。Linux Kernel
的开发和测试主要围绕合并窗口、rc（release candidate，候选发布版）阶段以及正式版发布展开：新功能先进入主线开发分支，在合并窗口结束后由
Linus Torvalds 本人发布多个 rc 版本，供内核开发者、硬件厂商、发行版维护者和测试者集中验证。这个阶段的重点是尽可能发现 Linux
Kernel 里的兼容性和性能问题，来确保正式版的稳定性。

整体来看，Windows、macOS 和 Linux 的测试流程虽然都包含「让一部分人先用，再逐步扩大测试范围」这一共性，但侧重点各不相同。

有了这样的背景知识以后，我们就能回答最开始的那个问题了。测试版的本质在于**
风险分层管理**，把没完成的软件在兼容性、稳定性、数据安全等方面的不确定性，按不同用户群体和发布阶段逐层向外扩展，在保护大多数用户的前提下，尽可能充分地暴露和修复问题。而对普通用户来说，清晰透明的频道分层也有助于降低他们在选择和使用测试版时的认知成本。

但如果像是过去的 Windows Insider
那样，喜欢用营销话术为主的宣传策略，那么风险分层的作用就会被大大削弱。用户根本搞不清自己到底在冒多大的险，测试体系本身的意义也就大打折扣了。好在微软已经意识到了这个问题，也承诺会做出改进。

## **Linux 系统的「年龄验证」闹剧**

[**@PlatyHsu**](https://sspai.com/u/platyhsu)**:** 作为自由软件世界的代表性项目，各大 Linux
发行版「自古以来」就充分贯彻了这种自由精神：你爱从哪下载就从哪下载，想怎么安装就怎么安装，没有人关心你的身份。不过，一场正在许多地方蔓延的「年龄验证」闹剧，可能会让这种自由逐渐成为过去。

「年龄验证」立法本身并不是什么新鲜事物。近年来最为典型的案例大概要数英国 2023
年的《[在线安全法](https://en.wikipedia.org/wiki/Online_Safety_Act_2023)》。但在过去，年龄验证立法的规管对象都是网站和在线服务，至多延伸到应用商店。直到加州于
2025 年 10 月通过了
[AB-1043](https://leginfo.legislature.ca.gov/faces/billTextClient.xhtml?bill_id=202520260AB1043)《数字年龄保证法》（Digital
Age Assurance Act），监管的手臂才第一次伸进了用户端的操作系统。

AB-1043 规定，从 2027 年 1 月 1
日起，操作系统提供者应当在账户设置阶段提供一个界面，要求账户持有人提供该设备用户的出生日期或年龄；还应当通过实时 API
向请求的应用响应一个不可识别个人身份的「年龄段信号」，将用户归入 13 岁以下、13–16 岁、16–18 岁，以及 18
岁以上四个区间之一。受规管的应用程序在被下载和首次启动时必须发出此类请求，并被视为已对其结果有「实际知情」，从而触发开发者在法律下基于用户年龄的各项义务。违反规定的最高罚款为每名受影响儿童
7,500 美元。

AB-1043 的效仿者众多。科罗拉多在议的 [SB26-051](https://leg.colorado.gov/bills/SB26-051)
法案几乎逐字复制了加州的措辞。巴西的 [Lei
15.211/2025](https://www.planalto.gov.br/ccivil_03/_ato2023-2026/2025/lei/L15211.htm)
还更进一步，要求未成年人下载任何应用都必须获得监护人同意。

显然，这些法案的荒谬之处在于，立法者认为所有操作系统都和苹果、微软和谷歌如今的产品一样，与自家的账号体系和网络服务高度绑定，并且有中心化的应用分发机制。但是，像
Debian、Arch 这样的 Linux
发行版都是由志愿者以非商业性质维护的，既没有账号体系，也没有公司实体，更没有庞大的客户支持和法律团队，因此没有任何技术和物质条件来履行与那些科技巨头同等程度的义务，却仍然被
AB-1043 及其效仿者一并囫囵纳入了受规管的范围。

对此，Linux 世界目前的反应大致分为妥协、观望和抵制三个阵营。

最先行动的大概要数许多发行版采用的系统管理框架 systemd。根据该项目三月合并的一个
[PR](https://github.com/systemd/systemd/pull/40954)，systemd 的用于记录用户信息的
`userdb` 中将会新增一个 `birthDate`
字段，以便其他开源项目在此基础上构建年龄验证功能。尽管这只是一个字段，本身不具备任何追踪功能，还是在评论区引起了很多争论和批评。例如，一种有代表性的质疑指出，AB-1043
和 SB26-051
实际上都不要求存储完整出生日期，只需年龄段即可，目前的设计反而引入了更隐私的信息。项目维护者随后拒绝了社区提出的回滚请求，并在评论数累计到九百多条后锁帖。至于围绕该字段的应用层接口则未有定论，目前至少有两种设计都以关闭
PR 告终。

主流发行版方面，Canonical 在 3 月 4 日的 [Discourse
帖子](https://discourse.ubuntu.com/t/ubuntus-response-to-californias-digital-
age-assurance-act-ab-1043/77948)中表示，正在与法务团队内部讨论，尚无具体计划。Fedora 项目负责人 Jef
Spaleta 则提出了一种设想，在账户创建时往 `/etc/` 创建一个文件，配合本地 API 宫有需要的应用读取，但目前并未付诸代码。Pop!_OS
的开发商 System76 则公开[反对](https://blog.system76.com/post/system76-on-age-
verification/)这类立法，并声称已经与科罗拉多 SB26-051 的共同提案人 Matt Ball
参议员见面，后者表示愿意考虑将开源软件排除在该法案之外。Arch Linux、NixOS 目前均保持沉默。

明确抵制的声音则主要来自一些小众项目。基于 AOSP 的移动发行版 GrapheneOS
[公开声明](https://x.com/GrapheneOS/status/2034957604682621229)，该系统不会要求提供任何个人信息、身份证明或账户；「如果
GrapheneOS 因为某些地区的监管要求不能在那里销售，那就也罢」。基于 FreeBSD 的发行版 MidnightBSD
则在许可证中加入了一个[条款](https://github.com/MidnightBSD/src?tab=License-1-ov-
file#:~:text=age%20verification)，规定任何所在地有法规要求操作系统提供年龄验证功能的用户，不得使用该操作系统。Arch
Linux 的社区维护 32 位分支 Arch Linux 32 则更是[屏蔽](https://linuxiac.com/linux-
distributions-begin-blocking-brazil-access-over-new-digital-law/)了来自加州和巴西的 IP
地址，称之为「预防性合规」。还有更激进者如 [Ageless Linux](https://agelesslinux.org/)
项目，制作了一个号称「公然不合规」的 Linux 发行版，并承诺持续提供脚本，用于移除其他发行版引入的年龄验证机制。

其实，暂且抛去技术上的可行性不谈，这类立法也有很多可商榷之处。

首先，很难相信年龄验证能够对这些法案声称要保护的未成年人提供有效的保护。AB-1043
一类法规目前只要求用户自报年龄，对于一个想下载应用的未成年用户而言，这与不存在并无区别。即使升级到基于身份证件或人脸检测，也只会给更多绕过的办法以产生恐惧——英国《在线安全法》生效后
VPN 安装量的激增就是一例。

其次，即使能提供一定程度的保护，根据[比例原则](https://zh.wikipedia.org/wiki/%E6%AF%94%E4%BE%8B%E5%8E%9F%E5%89%87)，也要考察成本和收益的高低。在保护作用值得质疑的情况下，是否值得承担在所有操作系统中存储用户年龄信息的隐私风险？那些与商业巨头不可同日而语的开源项目，要么被动承担合规成本，要么干脆把整个州或整个国家排除在外，由此对技术发展和普及造成的代价也不可忽略。

长期以来，Linux
长期以来对许多用户（尤其是年轻用户）的吸引力，正在于它赋予使用者充分的尊重，相信用户可以自行决定如何配置和使用，并对自己的决定负责。正如 System76
的 Carl Richell
提到，公司里大多数员工第一次安装操作系统时都还未成年，这些人「是出于好奇安装的，许多人后来开始写软件，有几个甚至就在写操作系统」。当世界各地的立法者打着「保护未成年人」的幌子，做着年龄验证的信息安全表演的时候，有没有想到自己也是在扼杀技术未来的种子呢？

## Apple 后台安全改进背后的细节

**@广陵止息：** Apple 在 3 月 18 日为 iOS 26.3.1、iPadOS 26.3.1、macOS 26.3.1
发布了首个后台安全改进，需要手动前往「设置」-「隐私与安全性」-「后台安全改进」安装。相比于正常的系统更新，「后台安全改进」的安装速度会快得多，下面我们就来聊聊
Apple 后台安全改进背后的细节。

Apple 从 Big Sur 开始为了系统安全性，就将 macOS 的系统卷和用户的数据卷分开了。Apple 把 macOS 的系统卷打包成了一个名叫
Signed System Volume（SSV）的东西，简单来说就是在启动 macOS 时会扫描整个系统卷，只要这个系统卷里改了任何一点东西，macOS
就会拒绝启动。所以，从那时候开始 Apple 任何的安全更新，都相当于对这个系统卷完整动一次手术。
